Le concept

La documentation

Le code dit ce que fait la machine ; il ne dit ni pourquoi, ni comment s'en servir, ni ce qui a été écarté. La documentation porte tout cela, pour un lecteur qui n'était pas là : un utilisateur, un collègue, un agent, ou toi dans six mois. Sa difficulté n'est pas de l'écrire, c'est qu'elle reste vraie.

50 min de lecture et de QCM Prérequis · 73 et 74 Exemples · DocumentationNomTests (SnapSet), README et Bubble (Cuttlefish), MagpieReglages

L'idée en une phrase

On écrit pour une question précise d'un lecteur précis, au plus près de ce qu'on documente, en évitant ce qui se périme vite ; et ce qui doit rester vrai, on le fait vérifier par un test.

L'analogie

Une maison. La notice de la chaudière (référence), le mot laissé au voisin pour arroser les plantes (guide), le plan de l'architecte avec ses raisons (explication). Personne ne cherche la vanne d'eau dans le plan de l'architecte.

À la fin, tu sais

  1. reconnaître les quatre sortes de documents ;
  2. écrire un commentaire qui dit pourquoi ;
  3. repérer ce qui se périme le plus vite ;
  4. faire vérifier la doc par un test.
À retenir Une documentation fausse est pire qu'une documentation absente : sans doc, on lit le code ; avec une doc fausse, on la croit. Chaque phrase écrite est une promesse qu'il faudra tenir à chaque modification du code.

Schéma 1 · Les commentaires

Dire pourquoi, pas quoi

Le commentaire le plus proche du code est aussi le plus lu. Il n'a pas à répéter ce que le code dit déjà mieux : il dit ce que le code ne peut pas dire, la raison d'un choix, l'alternative écartée, le piège évité.

magpie/plugin/Core/MagpieReglages.cs · lignes 12 à 15/// Stockés par Grasshopper lui-même (GH_SettingsServer) plutôt que dans un fichier /// à nous : un fichier de configuration rangé DANS le dossier de travail serait /// introuvable dès qu'on déplace ce dossier, et le réglage survit ainsi aux mises à /// jour du .gha. Voir issue #8.

L'alternative écartée

Ce commentaire nomme la solution rejetée (« un fichier à nous ») et la raison du rejet. Sans lui, le prochain lecteur pourrait la proposer de bonne foi. Le renvoi à l'issue #8 mène au débat complet.

Le résumé XML

/// <summary> documente ce qu'un appelant peut attendre d'un membre public ; Visual Studio l'affiche au survol. Le dossier src/ de SnapSet en compte 1 288, pour 76 fichiers C# (compté).

Piège courant Le commentaire qui paraphrase (« incrémente i ») : il double le texte à maintenir, et le jour où le code change sans lui, il ment. Si un commentaire explique ce que fait une ligne obscure, mieux vaut souvent renommer une variable ou extraire une méthode au nom parlant.

Schéma 2 · Une documentation qui se périme

Ce qui vieillit le plus vite

Toute doc vieillit, mais pas au même rythme. Un raisonnement reste vrai longtemps ; un nom de produit, un nombre de composants ou un numéro de ligne peuvent devenir faux au commit suivant, sans que personne ne relise la doc qui les cite.

Exemple autonome · désigner sans numéro de ligneFragile : « l'appel est à TrainingManager.cs:172 » Solide : « CompleteParcours appelle MagpieCertificateGenerator.Generate » Fragile : « les 20 composants » (vrai aujourd'hui : 20 classes, compté) Solide : « les composants, par ordre de travail : … »

Désigner par le nom

Un nom de méthode survit aux ajouts de lignes au-dessus d'elle, et se retrouve par une recherche. Le numéro de ligne n'a de sens que figé dans le temps : dans un message de commit, une revue, ou un cours comme celui-ci.

Au même endroit que le code

Plus la doc est loin du code, moins elle est relue quand il change. Un commentaire est vu à chaque modification ; un fichier de docs/, seulement si l'on pense à l'ouvrir. D'où l'intérêt d'un test qui l'ouvre à notre place.

Piège courant Mettre à jour le code « et la doc plus tard ». Plus tard n'arrive pas : la modification est faite, le contexte s'efface, et l'écart ne se voit qu'au moment où quelqu'un s'y fie. La doc concernée se modifie dans le même commit que le code.

Schéma 3 · La documentation dans l'interface

La doc que l'utilisateur lit vraiment

Un utilisateur de Grasshopper ouvre rarement un README. Il survole un composant, puis une entrée, et lit l'infobulle. Les chaînes passées au constructeur et à pManager.Add… sont donc la référence la plus lue d'un plugin.

cuttlefish/Bubble.cs · lignes 18 à 20 et 30, la 30 coupée: base("Bubble", "BUBL", "Draw a circle on each point, sized by the distance to its nearest neighbour", "Cuttlefish", "Draw") pManager.AddNumberParameter("Factor", "F", "The radius as a factor of half the distance to the nearest point (1 = bubbles touch).", GH_ParamAccess.item, 1);

Un README qui sert

Celui de Cuttlefish dit en une phrase ce que fait le plugin, puis présente les composants dans l'ordre du travail (points, transformer, dessiner) avec un tableau de référence. On sait en une minute si l'outil répond à son besoin.

La langue du lecteur

Cuttlefish, destiné au public, est documenté en anglais ; SnapSet et Magpie, en français, pour leurs utilisateurs et pour toi. Le choix vaut pour un projet entier : mélanger les deux dans une même interface déroute.

Piège courant La description qui répète le nom : « Factor : the factor ». Elle occupe la place sans répondre à la question du lecteur, qui est toujours la même : quelle valeur mettre, et que se passe-t-il si je la change ?

Explication

Péremption
L'écart qui se creuse entre une doc et le code qui a changé.
Source de vérité
L'endroit unique où une information est définie ; les autres la citent.
