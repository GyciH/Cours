Le concept

Modéliser des données

Avant d'écrire une requête, on décide quelles tables existent, ce qui identifie une ligne et comment les tables se citent. Ce découpage, le modèle de données, fixe ce que la base peut garantir seule et ce que le code devra surveiller. Un fait rangé à deux endroits finit toujours par dire deux choses différentes.

45 min de lecture et de QCM Prérequis · 34 Exemples · db.mjs, exercises.mjs, compute-proxy.mjs (Magpie)

L'idée en une phrase

Une table par sorte de chose, une clé qui ne change jamais pour chaque ligne, des liens par clé étrangère, et chaque fait à un seul endroit.

L'analogie

Un carnet d'adresses où l'on écrit l'adresse d'un ami sur sa fiche, et nulle part ailleurs. Celui qui la recopie dans chaque lettre devra toutes les corriger quand l'ami déménage.

À la fin, tu sais

  1. choisir une clé primaire ;
  2. placer une clé étrangère ;
  3. repérer un fait rangé deux fois ;
  4. décider entre colonnes et JSON.
À retenir Le cours 34 a montré comment lire et écrire dans magpie.db. Ce bloc regarde la base elle-même : sa forme ici, puis les requêtes, les index, les transactions, les accès simultanés et les sauvegardes.

Schéma 1 · Clés et contraintes

Ce que la base garantit seule

La clé primaire identifie une ligne : deux lignes ne peuvent pas la partager. La clé étrangère oblige une valeur à exister dans une autre table. STRICT impose le type de chaque colonne. Ces règles sont vérifiées à chaque écriture, quel que soit le code qui écrit.

magpie/web/db.mjs · lignes 39 à 50 (extrait)-- id reprend directement le "Id" du JSON natif Magpie (ex: "ex01_impairs"), pour -- pouvoir réimporter un exercice existant sans jamais changer sa référence. … CREATE TABLE IF NOT EXISTS exercises ( id TEXT PRIMARY KEY, parcoursId TEXT REFERENCES parcours(id),

Une clé naturelle

Magpie prend pour clé l'identifiant écrit dans le fichier de l'exercice, ex01_impairs, plutôt qu'un numéro attribué par la base. Réimporter le fichier retombe sur la même ligne. Le prix : cet identifiant ne doit jamais être renommé.

STRICT convertit sans perte

La mesure nuance le cours 34 : STRICT refuse "abc" et 2.5 dans une colonne entière, mais range "7" comme l'entier 7, parce que la conversion ne perd rien. Sans STRICT, "abc" est rangé tel quel.

Piège courant Croire qu'une clé étrangère est toujours vérifiée. SQLite ne le fait que si on l'active ; node:sqlite l'active par défaut, mais un autre outil ouvrant magpie.db (un client graphique, l'outil sqlite3) peut accepter des orphelins.

Schéma 2 · La normalisation

Un fait, un seul endroit

Normaliser, c'est ranger chaque information là où elle dépend de la clé, une seule fois. Copier une information ailleurs, pour la lire plus vite ou plus simplement, s'appelle dénormaliser : c'est permis, à condition que chaque écriture mette les deux copies à jour.

magpie/web/exercises.mjs · lignes 24 à 28 (extrait)if (!current.parcoursId) { for (const p of db.prepare("SELECT id, exerciseIds FROM parcours WHERE exerciseIds IS NOT NULL").all()) { const index = JSON.parse(p.exerciseIds).indexOf(config.Id); if (index === -1) continue; db.prepare("UPDATE exercises SET parcoursId = ?, sortOrder = ? WHERE id = ?").run(p.id, index, config.Id);

Pourquoi deux copies

La liste exerciseIds sert à rattacher un exercice importé après son parcours : la base doit se souvenir de la place qu'on lui réservait. L'ordre réel, lui, vit dans sortOrder. Deux rôles proches, deux endroits.

La forme normalisée

Une table de liaison, une ligne par place réservée, avec ou sans exercice importé, porterait à la fois l'appartenance et la position. Le réordonnancement n'aurait qu'un endroit à changer, et les deux usages liraient la même donnée.

Piège courant Ajouter une copie « pour simplifier » sans écrire, au même moment, le code qui la tient à jour. La base ne sait pas que deux colonnes disent la même chose : rien ne signale leur divergence.

Schéma 3 · Les relations

Un, plusieurs, et le JSON

Le sens d'une relation décide de la place de la clé étrangère. Un parcours a plusieurs exercices : la clé va dans exercises. Si un exercice devait vivre dans plusieurs parcours, aucune des deux tables ne suffirait : il faudrait une table de liaison.

Exemple autonome · SQLite, une table de liaison (Magpie n'en a pas)CREATE TABLE parcours_exercices ( parcoursId TEXT NOT NULL REFERENCES parcours(id), exerciseId TEXT NOT NULL REFERENCES exercises(id), position INTEGER NOT NULL, PRIMARY KEY (parcoursId, exerciseId) -- un lien, une seule fois ) STRICT;

Quand le JSON va bien

validationConfig se lit toujours en entier, par l'exercice, et n'est jamais cherché par son contenu. Le découper en colonnes n'apporterait rien, et le JSON reste celui du plugin, sans traduction. C'est le bon usage d'une colonne JSON.

Quand il gêne

Dès qu'on cherche, trie ou relie par une valeur cachée dans le JSON, la base ne peut ni l'indexer simplement ni la contrôler. exerciseIds est dans ce cas : on y cherche un identifiant, en relisant tous les parcours.

Piège courant Ranger une liste d'identifiants dans une colonne texte, séparés par des virgules ou en JSON, pour éviter une table de liaison. Aucune clé étrangère ne peut alors vérifier que ces identifiants existent.

Glossaire

Modèle de données
Le découpage en tables, clés et liens.
Clé naturelle
Une clé prise dans la donnée elle-même, comme un identifiant de fichier.
Clé étrangère
Une colonne dont chaque valeur doit exister dans une autre table.
Normalisation
Ranger chaque fait à un seul endroit.
Table de liaison
Une table dont chaque ligne relie deux lignes d'autres tables.
