Le concept

Versionner : SemVer et compatibilité

Un numéro de version n'est pas un compteur de sorties : c'est une promesse faite à ceux qui dépendent de ton code. Le versionnage sémantique (SemVer) range cette promesse en trois nombres, et les outils comme npm s'en servent pour décider seuls quelle mise à jour ils ont le droit d'installer.

50 min de lecture et de QCM Prérequis · 04 et 65 Exemples · Directory.Build.props, ImportParcours, package.json (Magpie)

L'idée en une phrase

Le premier nombre dit « attention, ça casse », le deuxième « il y a du nouveau », le troisième « c'est réparé » ; tout le reste (plages, verrous, formats de fichier) découle de cette convention.

L'analogie

Une prise électrique. Changer le fusible (correctif) ou ajouter un port USB à côté (mineur) ne gêne aucun appareil ; changer la forme des broches (majeur) oblige chacun à acheter un adaptateur.

À la fin, tu sais

  1. choisir le nombre à incrémenter ;
  2. lire une plage npm (^, ~, exacte) ;
  3. dire à quoi sert le fichier de verrouillage ;
  4. versionner un format de fichier.
À retenir Ce qui « casse » se juge du point de vue de celui qui t'utilise : renommer une méthode publique, retirer un champ d'un JSON, changer le sens d'un paramètre. Un changement interne invisible de l'extérieur n'est jamais majeur, même s'il a demandé beaucoup de travail.

Schéma 1 · Les plages de versions

Ce que j'accepte d'installer

Dans package.json, on n'écrit pas une version mais une plage : l'ensemble des versions qu'on juge compatibles. npm prend ensuite la plus récente de la plage. Les réponses ci-dessous ont été calculées par la bibliothèque semver fournie avec npm.

magpie/web/package.json · lignes 13 à 21, commentaires ajoutés"@xyflow/react": "^12.3.6", // tout 12.x.y à partir de 12.3.6 "react": "^18.3.1", "rhino3dm": "8.35.0", // exactement celle-ci "three": "0.186.1", // idem : une 0.x change à chaque mineur "vite": "^5.4.11" // (devDependencies)

Le chapeau et la tilde

^ accepte tout ce qui ne change pas le premier nombre non nul ; ~ n'accepte que des correctifs. Le chapeau est le choix par défaut de npm install paquet : il fait confiance à l'auteur pour respecter SemVer.

Pourquoi figer rhino3dm et three

Une version 0.x ne promet rien d'un mineur à l'autre, et three.js change parfois d'API entre deux mineurs. Écrire la version exacte, c'est décider soi-même du moment de la mise à jour, et la tester.

Piège courant Croire que ^0.1.5 accepte 0.2.0. Avant 1.0.0, le chapeau fige aussi le deuxième nombre, puisque c'est lui qui joue le rôle de majeur. Une bibliothèque en 0.x peut tout casser au passage de 0.1 à 0.2.

Schéma 2 · Le fichier de verrouillage

Ce que j'ai réellement installé

Une plage laisse une marge, et la plus récente version d'aujourd'hui n'est pas celle de demain. Le fichier package-lock.json note la version choisie pour chaque paquet, dépendances des dépendances comprises : deux installations faites à six mois d'écart donnent alors le même résultat.

Exemple autonome · terminal, dans web/npm ci # installe le verrou tel quel (serveur, intégration) npm install # installe, complète le verrou si besoin (poste) npm outdated # liste ce qui a vieilli, sans rien changer npm install three@0.187.0 # monte une version figée, à la main

Le verrou se versionne

package-lock.json se commite avec le code, comme package.json. Celui de Magpie est au format lockfileVersion: 3 (ligne 4) : le fichier lui-même a un numéro de format, pour que npm sache le lire.

Et en .NET ?

<PackageReference Version="2.9.2"/> désigne la version minimale, et NuGet prend la plus basse qui convient : sans plage ouverte, le résultat est stable. Un verrou existe aussi (packages.lock.json), à activer.

Piège courant Supprimer package-lock.json « pour réparer » une installation. npm reprend alors la plus récente version de chaque plage, dépendances indirectes comprises : on règle peut-être un problème, et on en importe dix autres qu'on n'a pas testés.

Schéma 3 · Versionner un format

Un fichier qui survit aux versions du logiciel

Un fichier enregistré aujourd'hui sera rouvert par la version de demain, et parfois par celle d'hier. Écrire dans le fichier le numéro de son format permet au lecteur de décider, avant de lire le reste, s'il sait le comprendre.

Exemple autonome · C# et JavaScriptnew Version("0.1.10") > new Version("0.1.9") // true : nombre par nombre "0.1.10" < "0.1.9" // true en JS : texte ! ["0.1.9", "0.1.10", "0.2.0"].sort() // [ '0.1.10', '0.1.9', … ]

Compatible dans les deux sens

Lire les anciens fichiers, c'est la compatibilité ascendante : on la doit toujours. Lire un fichier plus récent, c'est la compatibilité descendante : on l'obtient en ignorant les champs inconnus, tant que le format n'a pas changé de sens.

Ajouter sans casser

Un champ nouveau, facultatif, avec une valeur par défaut raisonnable, ne casse personne : c'est l'équivalent d'un mineur. Renommer un champ ou changer son unité, c'est un nouveau format, donc un nouveau numéro.

Piège courant Ajouter le numéro de format « plus tard, quand on en aura besoin ». Les fichiers déjà diffusés n'en ont pas, et le jour venu, rien ne distingue un vieux fichier d'un fichier abîmé. C'est pourquoi ImportParcours le lit dès la première version.

Glossaire

SemVer
Le versionnage sémantique : majeur.mineur.correctif, chacun avec sa promesse.
Plage
L'ensemble des versions qu'une dépendance accepte, comme ^12.3.6.
Verrou
Le fichier qui note la version réellement choisie de chaque paquet.
Compatibilité ascendante
La nouvelle version sait lire et servir ce que l'ancienne produisait.
Version de format
Le numéro d'un format de fichier, distinct de celui du logiciel.
