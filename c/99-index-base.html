Le concept

Les index d'une base

Sans aide, une base qui cherche les exercices d'un parcours lit toute la table. Un index range à part les valeurs d'une colonne, triées, avec l'adresse de chaque ligne : la recherche descend un arbre au lieu de tout lire. C'est l'index spatial du cours 93, pour des valeurs qu'on peut trier.

45 min de lecture et de QCM Prérequis · 55, 93 et 98 Exemples · db.mjs, compute-proxy.mjs, authorize-components.mjs (Magpie)

L'idée en une phrase

Un index transforme une lecture de toute la table en une descente de quelques pages, au prix d'un peu de place et d'écritures plus lentes.

L'analogie

L'index à la fin d'un livre : pour trouver « transaction », on ne relit pas les 400 pages, on va à la lettre T. Mais chaque nouvelle page du livre oblige à remettre l'index à jour.

À la fin, tu sais

  1. lire un plan de requête ;
  2. choisir les colonnes d'un index ;
  3. repérer ce qui empêche un index ;
  4. peser son coût en écriture.
À retenir Une clé primaire est toujours indexée : SQLite crée seul un index pour id TEXT PRIMARY KEY. Les autres colonnes ne le sont que si on écrit CREATE INDEX. Toutes les mesures de ce cours ont été faites avec node:sqlite, en mémoire.

Schéma 1 · Le gain

Lire tout, ou descendre l'arbre

Un parcours complet coûte en proportion du nombre de lignes : O(n), cours 55. Une descente d'arbre coûte en proportion de sa profondeur, qui grandit comme log n. Sur une petite table, la différence ne se voit pas ; sur un million de lignes, elle devient un facteur de plusieurs centaines.

Exemple autonome · SQLite, l'index du schéma (Magpie n'en a pas)CREATE INDEX ix_ex_ordre ON exercises(parcoursId, sortOrder, title); -- la requête de compute-proxy.mjs, ligne 244, s'en sert sans changer : SELECT … FROM exercises WHERE parcoursId = ? ORDER BY sortOrder, title;

Rien à changer dans la requête

On n'écrit jamais « utilise tel index » : le planificateur voit l'index et décide seul de s'en servir. Ajouter un index ne casse donc aucune requête ; il peut seulement en accélérer, ou ralentir les écritures.

À 1 000 lignes, rien ne se voit

149 µs sans index, 100 µs avec : l'essentiel du temps sert à rendre les 100 lignes. Le parcours complet ne devient gênant qu'à partir de dizaines de milliers de lignes, où il passe à 10 puis 75 ms.

Piège courant Mesurer sur la petite base de développement et conclure qu'un index est inutile. Le coût d'un parcours complet grandit avec les données ; on mesure à la taille attendue, ou on lit le plan.

Schéma 2 · Le plan de requête

Demander à la base ce qu'elle fera

EXPLAIN QUERY PLAN devant une requête rend le chemin choisi, sans l'exécuter. SCAN veut dire « toute la table », SEARCH … USING INDEX « par l'index », et USE TEMP B-TREE qu'il faudra encore trier le résultat.

Exemple autonome · Node, lire le plan d'une requêteconst plan = db.prepare("EXPLAIN QUERY PLAN " + sql).all(); console.log(plan.map((r) => r.detail).join(" | ")); // SEARCH exercises USING INDEX ix_ex_ordre (parcoursId=?)

L'ordre des colonnes compte

L'index (parcoursId, sortOrder, title) est trié d'abord par parcours, puis par position, puis par titre : exactement le filtre et le tri de la requête. Rangé (sortOrder, parcoursId), il ne servirait plus à trouver un parcours.

La clé primaire

Le plan de WHERE id = ? montre SEARCH … USING INDEX sqlite_autoindex_exercises_1 : l'index que SQLite a créé seul pour la clé primaire. Toutes les lectures de Magpie par identifiant passent par lui, en 2 µs.

Piège courant Créer un index par colonne « au cas où ». Une requête n'en utilise généralement qu'un par table, et chacun ralentit toutes les écritures. On crée l'index qu'une requête lente réclame, plan à l'appui.

Schéma 3 · Les limites

Ce qui empêche un index, ce qu'il coûte

Un index range les valeurs telles quelles. Une requête qui les transforme avant de comparer, ou qui cherche au milieu d'un texte, ne peut pas descendre l'arbre. Et chaque insertion doit ranger la nouvelle valeur dans chaque index.

Exemple autonome · SQLite, deux façons d'indexer une recherche sans casseCREATE INDEX ix_dn_low ON components(LOWER(displayName)); -- index d'expression CREATE INDEX ix_dn_nc ON components(displayName COLLATE NOCASE); SELECT … WHERE displayName = ? COLLATE NOCASE; -- se sert du second

Indexer l'expression

Un index d'expression range LOWER(displayName) au lieu de la colonne : la requête de Magpie, telle qu'elle est écrite, s'en servirait. COLLATE NOCASE fait le même travail par une règle de comparaison. Les deux ignorent la casse de l'ASCII seulement, comme LOWER.

Le texte au milieu

LIKE '%mot%' ne sait pas par où commencer dans l'ordre alphabétique : il lit tout. Une recherche plein texte se fait avec un index dédié (le module FTS5 de SQLite), qui découpe le texte en mots.

Piège courant Croire qu'un index sur displayName accélère LOWER(displayName) = ?. Le plan dit SCAN : 12,4 ms au lieu de 10 µs, mesuré, avec l'index pourtant présent.

À surveiller · aucun index secondaire, à revoir si la base grossit Le catalogue compte 727 composants (src/data/catalog.json) : la recherche de la ligne 22 les lit tous en 106 µs, mesuré sur une table de même taille. Les exercices se comptent par dizaines. Rien ne justifie un index aujourd'hui. Si un jour la base gardait l'historique des soumissions, des dizaines de milliers de lignes cherchées par exercice, un CREATE INDEX sur la colonne cherchée serait la première chose à écrire. Déduit des mesures de ce cours.

Glossaire

Index
Une structure triée qui mène d'une valeur aux lignes qui la portent.
Arbre B
Un arbre de pages triées, peu profond, où vivent les tables et les index de SQLite.
Plan de requête
Le chemin que la base a choisi pour exécuter une requête.
Parcours complet
La lecture de toutes les lignes d'une table (SCAN).
Index d'expression
Un index sur le résultat d'une fonction de la colonne.
