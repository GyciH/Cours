Le concept

La gestion des erreurs

Un programme utile rencontre des fichiers abîmés, des réseaux coupés, des saisies absurdes. Gérer les erreurs, ce n'est pas les faire taire : c'est décider, pour chacune, qui la traite, ce qu'on dit et à qui, et dans quel état on laisse les choses. Le reste du programme peut alors compter sur ce qui a réussi.

50 min de lecture et de QCM Prérequis · 59 et 75 Exemples · ImportParcours, MagpieParcoursLauncher, compute-proxy (Magpie)

L'idée en une phrase

Le code qui constate une erreur la signale ; le code qui la comprend la traduit ; le code qui sait ce que l'utilisateur attend décide quoi lui dire. Entre les deux, une exception remonte d'elle-même la pile d'appels.

L'analogie

Un colis refusé à la livraison. Le livreur constate (« adresse introuvable »), le service client traduit (« votre adresse semble incomplète »), et c'est toi qui décides de corriger ou d'annuler. Le livreur ne t'appelle pas pour en discuter.

À la fin, tu sais

  1. distinguer erreur attendue et bug ;
  2. attraper au bon endroit ;
  3. traduire une exception technique ;
  4. choisir entre exception, booléen, null et résultat.
À retenir Une exception non attrapée n'est pas un échec de la gestion d'erreurs : c'en est souvent la bonne fin, pour un bug. Le vrai échec, c'est l'erreur attrapée puis oubliée, qui laisse le programme continuer dans un état faux.

Schéma 1 · Attendu ou imprévu

Deux familles, deux traitements

Un fichier mal formé fait partie de la vie d'un programme d'import : on l'attend, on le décrit, on continue. Une référence nulle dans ton propre code est un bug : aucun message soigné ne le répare, il faut qu'il se voie.

magpie/web/compute-proxy.mjs · lignes 84 à 98, resserrées et commentéesclass HttpError extends Error { constructor(status, message, code) { super(message); this.status = status; // 400, 502, 504… : pour le client HTTP this.code = code; // "INVALID_JSON" : stable, pour un programme } } function parseJsonBody(body) { try { return JSON.parse(body); } catch { throw new HttpError(400, "Corps de requête JSON invalide.", "INVALID_JSON"); } }

Une classe pour l'attendu

HttpError marque les erreurs prévues, présente sur 23 lignes du fichier. Son code ne change pas quand on reformule le message ; un programme peut donc s'y fier, comme le navigateur de l'élève.

Message propre, détail caché

Le message natif de JSON.parse("{nodes:") est « Expected property name or '}' in JSON at position 1 » (mesuré) : exact, mais pas pour un client. parseJsonBody le remplace par une phrase et un code.

Piège courant Un catch (Exception) autour de tout, « par sécurité ». Il attrape aussi les bugs, leur donne l'apparence d'une erreur attendue, et la pile disparaît. On attrape les types qu'on sait traiter, et on laisse passer le reste.

Schéma 2 · Traduire à la frontière

De la bibliothèque à l'humain

Une bibliothèque JSON ne sait pas qu'elle lit un parcours Magpie ; elle dit ce qu'elle voit. La couche qui sait de quoi il s'agit traduit l'exception dans son vocabulaire à elle. La couche d'interface, enfin, choisit la forme : une bulle, une boîte de dialogue, une réponse HTTP.

magpie/plugin/Student/MagpieParcoursLauncher.cs · lignes 214 à 219, commentaire ajoutécatch (Exception ex) when (ex is InvalidDataException || ex is IOException || ex is UnauthorizedAccessException) { Signaler(GH_RuntimeMessageLevel.Error, $"Import impossible : {ex.Message}"); return; } if (r == null) return; // annulé par l'utilisateur : pas une erreur

Le filtre when

catch (…) when (condition) n'attrape que si la condition est vraie ; sinon l'exception continue comme si le catch n'existait pas, pile intacte. Ici : trois types attendus, et tout le reste remonte.

Garder la cause

En traduisant, on peut garder l'exception d'origine : throw new InvalidDataException("…", ex). Elle reste lisible dans InnerException et dans ex.ToString(), pour le journal (cours 75).

Piège courant throw ex; au lieu de throw; pour relancer une exception attrapée. En C#, la première forme repart de la ligne courante et efface la pile d'origine ; la seconde la conserve. Pour relancer telle quelle, on écrit throw; seul.

Schéma 3 · Signaler sans exception

Choisir la forme de l'échec

L'exception n'est pas la seule manière de dire qu'une chose a échoué. Elle convient au cas anormal pour l'appelant. Quand l'échec est courant, ou qu'il n'est qu'à moitié un échec, une valeur de retour le dit mieux et coûte moins cher.

Exemple autonome · C# et JavaScriptif (int.TryParse(texte, out int n)) Utiliser(n); // l'échec est un cas normal else Avertir("Ce n'est pas un nombre entier."); Number("12abc") // NaN (mesuré) : à tester avec Number.isNaN const r = await Promise.allSettled(taches); // succès et échecs, côte à côte

Nettoyer quoi qu'il arrive

finally s'exécute après le try, qu'il ait réussi, levé une exception ou fait return. C'est la place des nettoyages : dossier temporaire, fichier ouvert, verrou (cours 67). using en est la forme courte.

Le catch vide, justifié

Avaler une exception peut être juste, si l'échec est sans conséquence. Alors on le dit dans le code : pourquoi on l'ignore, et pourquoi ce n'est pas grave. Le prochain lecteur ne prendra pas ce silence pour un oubli.

Piège courant Rendre null pour plusieurs raisons différentes : fichier absent, fichier vide, annulation. L'appelant ne peut plus distinguer, et finit par tout traiter pareil. null pour un seul sens, une exception ou un résultat détaillé pour le reste.

Glossaire

Exception
Un objet qui interrompt le cours normal et remonte la pile jusqu'à un catch.
Erreur attendue
Un échec prévu par le métier, qu'on décrit et dont on se remet.
Filtre d'exception
La clause when qui décide si un catch s'applique.
Traduction
Remplacer une exception technique par une exception du domaine, cause gardée.
finally
Le bloc qui s'exécute à la sortie du try, quelle qu'en soit la manière.
