Le concept

Processus, threads et verrous

Un processus est un programme en cours d'exécution, avec sa propre mémoire. Un thread (ou fil d'exécution) est une suite d'instructions qui s'exécute dans un processus ; il peut y en avoir plusieurs, qui avancent en même temps et partagent la même mémoire. C'est leur force, et la source de bugs parmi les plus sournois.

50 min de lecture et de QCM Prérequis · 44 et 59 Exemples · MesureurGdi, Constituant (SnapSet), ChargeurCore (Magpie)

L'idée en une phrase

Deux threads qui touchent la même donnée sans se coordonner peuvent produire un résultat faux, et pas à chaque fois : on protège chaque donnée partagée par un verrou, ou on évite de la partager.

L'analogie

Deux cuisiniers dans la même cuisine (threads d'un processus) partagent le plan de travail ; deux restaurants (processus) ont chacun le leur. Le verrou, c'est la règle « un seul à la fois devant la balance ».

À la fin, tu sais

  1. distinguer processus et thread ;
  2. reconnaître une situation de course ;
  3. poser un verrou, éviter l'interblocage ;
  4. respecter le fil d'interface.
À retenir Un processeur à 4 cœurs exécute vraiment 4 threads à la fois ; au-delà, le système les fait alterner des milliers de fois par seconde, à des instants que le programme ne choisit pas. Tout raisonnement du type « ça n'arrivera jamais entre ces deux lignes » est faux.

Schéma 1 · La situation de course

Un bug qui ne se montre pas à chaque fois

Une situation de course (race condition) survient quand le résultat dépend de l'ordre dans lequel les threads s'entrelacent. La mesure ci-dessous a été faite pour ce cours : le même programme, lancé huit fois, donne quatre fois le bon résultat et quatre fois un résultat faux, chaque fois différent.

Exemple autonome · C#compteur++; // FAUX si plusieurs threads lock (verrou) { compteur++; } // juste : un seul thread à la fois Interlocked.Increment(ref compteur); // juste et plus rapide, pour un entier seul var cache = new ConcurrentDictionary<string, Font>(); // collection déjà protégée

Pourquoi c'est si traître

Sur la machine du développeur, le bug peut ne jamais apparaître ; chez un utilisateur plus chargé, une fois par jour. Le débogueur, en ralentissant tout, le fait souvent disparaître. On ne le corrige pas en le reproduisant : on le corrige en raisonnant.

Les collections ordinaires

List, Dictionary et HashSet ne sont pas faites pour être modifiées par deux threads à la fois : au mieux une exception, au pire une structure interne abîmée. La lecture seule, sans aucune écriture, est sans danger.

Piège courant Vérifier puis agir en deux temps : if (!dico.ContainsKey(k)) dico[k] = v;. Entre le test et l'écriture, un autre thread peut faire la même chose. Le test et l'action doivent être dans le même verrou, ou en une seule opération comme GetOrAdd.

Schéma 2 · Le verrou et l'interblocage

Protéger, sans se bloquer

Le bloc lock (objet) { … } de C# garantit qu'un seul thread à la fois exécute une section protégée par ce même objet. Les autres attendent à l'entrée. Mais deux threads qui attendent chacun un verrou tenu par l'autre attendront pour toujours : c'est l'interblocage (deadlock).

Exemple autonome · C#private readonly object _verrou = new object(); // objet privé, rien d'autre lock (_verrou) { /* court : pas d'attente, pas d'appel inconnu */ } // à éviter : lock (this), lock (typeof(X)), lock ("texte") // en async : await interdit dans un lock -> SemaphoreSlim.WaitAsync()

Sur quoi verrouiller

Un objet privé, que personne d'autre ne peut verrouiller. Avec this ou une chaîne, un code extérieur peut prendre le même verrou sans le savoir, et créer un interblocage introuvable.

Le coût

Un verrou que personne ne dispute coûte quelques dizaines de nanosecondes. Le vrai coût vient de l'attente quand il est disputé : on garde donc la section protégée la plus courte possible, sans entrée-sortie ni appel réseau dedans.

Piège courant Appeler, à l'intérieur d'un verrou, un événement ou une méthode fournie par quelqu'un d'autre. On ne sait pas ce qu'elle fait : si elle prend un autre verrou, ou attend le fil d'interface, l'interblocage est servi. On copie ce qu'il faut sous le verrou, puis on appelle dehors.

Schéma 3 · Le fil d'interface

Un seul thread pour l'écran

Les interfaces Windows (WinForms, Eto dans Rhino) confient tout l'affichage à un seul thread, qui traite une file de messages. C'est une façon d'éviter les verrous : ce qui ne vit que sur ce fil n'est jamais partagé. Le prix : un travail long sur ce fil fige toute la fenêtre (cours 44).

Exemple autonome · C# dans Rhinovar resultat = await Task.Run(() => CalculLong(donnees)); // ailleurs etiquette.Text = resultat; // après await : de retour sur le fil d'interface // hors async, depuis un autre fil : RhinoApp.InvokeOnUiThread(new Action(() => doc.Views.Redraw()));

Et Grasshopper ?

La solution, la peinture du canvas et les événements de souris passent tous par le fil d'interface. C'est pourquoi un composant lent fige Rhino entier, et pourquoi un plugin ne doit modifier le document que depuis ce fil.

Et Node ?

Ton code JavaScript tourne sur un seul thread, avec une boucle d'événements (cours 59) : pas de course entre deux lignes de JS. Les entrées-sorties se font dans d'autres threads, et worker_threads en crée pour le calcul.

Piège courant Bloquer le fil d'interface en attendant une tâche avec .Result ou .Wait(). Si la tâche a besoin de revenir sur ce fil pour finir, chacun attend l'autre : c'est un interblocage, sans aucun lock écrit. Avec une tâche, on await.

Glossaire

Processus
Un programme en cours d'exécution, avec sa mémoire propre.
Thread
Un fil d'exécution dans un processus, qui partage sa mémoire avec les autres.
Situation de course
Un résultat qui dépend de l'ordre d'entrelacement des threads.
Verrou
Un mécanisme qui ne laisse entrer qu'un thread à la fois dans une section.
Interblocage
Des threads qui s'attendent mutuellement, pour toujours.
