Le concept

Les transactions

Une modification réelle demande souvent plusieurs écritures : recréer deux tables, puis y remettre les lignes ; réordonner dix exercices. Si le programme s'arrête au milieu, la base garde une moitié de modification. Une transaction regroupe ces écritures : la base les applique toutes, ou aucune.

45 min de lecture et de QCM Prérequis · 76 et 97 Exemples · db.mjs, exercises.mjs, compute-proxy.mjs (Magpie)

L'idée en une phrase

Tout ce qui doit réussir ensemble s'écrit entre BEGIN et COMMIT ; au moindre échec, ROLLBACK remet la base exactement comme avant.

L'analogie

Un virement : débiter un compte et créditer l'autre. La banque ne doit jamais s'arrêter entre les deux. Soit l'argent a changé de compte, soit rien ne s'est passé.

À la fin, tu sais

  1. dire ce que garantit ACID ;
  2. écrire une transaction sûre en Node ;
  3. accélérer des écritures en série ;
  4. repérer une modification en plusieurs temps.
À retenir Les mesures de ce cours ont été faites sur un vrai fichier SQLite, pas en mémoire : la durabilité, et donc son coût, n'existe que sur disque. Le journal par défaut de SQLite (mode delete) et la synchronisation complète étaient actifs.

Schéma 1 · Le prix d'un COMMIT

Valider coûte, travailler non

Pour qu'une validation survive à une coupure de courant, SQLite écrit un journal, puis attend que le disque confirme avoir tout rangé. Cette attente se paie à chaque COMMIT, pas à chaque ligne. Regrouper mille écritures en une transaction, c'est attendre une fois au lieu de mille.

Exemple autonome · node:sqlite, la version rapide du schémaconst ins = db.prepare("INSERT INTO t (v) VALUES (?)"); db.exec("BEGIN"); for (let i = 0; i < N; i++) ins.run("x" + i); // rien n'est encore attendu db.exec("COMMIT"); // une seule attente du disque

Une transaction implicite

Sans BEGIN, SQLite ouvre et valide une transaction autour de chaque instruction : c'est le mode « autocommit ». Chaque run d'une boucle paie donc sa propre attente du disque, 1,3 ms mesurée ici.

Pour un import

Les scripts d'import de Magpie écrivent quelques dizaines de lignes : quelques dizaines de millisecondes d'attente, invisibles. Le même code sur dix mille lignes prendrait quinze secondes, contre dix-sept millisecondes en une transaction.

Piège courant Mesurer des écritures sur une base en mémoire et conclure qu'elles sont rapides. En mémoire, il n'y a pas de disque à attendre : l'autocommit y semble gratuit, et ne l'est plus dès qu'on passe au fichier.

Schéma 2 · Tout ou rien

Un arrêt au milieu

Un processus peut s'arrêter n'importe où : une exception non rattrapée, une fenêtre fermée, une coupure de courant. Les écritures déjà validées restent. Sans transaction, chaque instruction est validée à part : l'arrêt laisse un état que personne n'a voulu.

Des données en mémoire seulement

Entre le DROP et la fin de la boucle, les exercices n'existent que dans le tableau JavaScript existingExercises. Un arrêt dans cet intervalle les perd. Et comme le nouveau schéma est déjà créé, la migration ne se relancera pas.

Avec une transaction

Le DROP, le CREATE et les insertions deviennent un seul changement. À la réouverture, SQLite trouve le journal inachevé et remet l'ancien état : l'ancien schéma revient, la migration repart. La mesure le confirme.

Piège courant Croire qu'une migration « qui s'exécute en une fraction de seconde » n'a pas besoin de transaction. La durée de la fenêtre réduit le risque, elle ne le supprime pas ; la transaction le supprime pour rien.

Schéma 3 · Écrire une transaction

BEGIN, try, COMMIT, catch, ROLLBACK

node:sqlite n'offre pas de méthode qui enveloppe une fonction dans une transaction : on écrit BEGIN et COMMIT soi-même. Une erreur au milieu ne referme rien toute seule, c'est au code de l'annuler (cours 76).

Exemple autonome · node:sqlite, une fonction utilitaire de transactionfunction enTransaction(db, travail) { db.exec("BEGIN"); try { const r = travail(); db.exec("COMMIT"); return r; } catch (e) { if (db.isTransaction) db.exec("ROLLBACK"); // annuler, puis laisser l'erreur remonter throw e; } }

Relancer l'erreur

Le catch annule, puis relance : l'appelant doit savoir que rien n'a été écrit. Avaler l'erreur ferait croire à un succès, pour une base restée inchangée.

Pas d'attente dedans

Une transaction tient un verrou sur la base (cours 101). On n'y place pas d'appel réseau ni d'await : on prépare les données avant, on écrit d'un trait, on valide.

Piège courant Oublier le ROLLBACK dans le catch. La transaction reste ouverte, mesuré : le BEGIN suivant échoue, et les écritures suivantes s'ajoutent à un travail que personne ne validera.

Glossaire

Transaction
Un groupe d'écritures appliqué entièrement ou pas du tout.
ACID
Atomicité, cohérence, isolation, durabilité : ce qu'une transaction garantit.
Autocommit
Le mode où chaque instruction forme sa propre transaction.
Journal
Le fichier qui permet à SQLite de défaire ou terminer une transaction après un arrêt.
Retour arrière
L'annulation d'une transaction (ROLLBACK).
