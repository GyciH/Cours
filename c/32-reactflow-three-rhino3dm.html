Le concept

React Flow, three.js
et rhino3dm

Trois bibliothèques, trois métiers. React Flow dessine le canvas de nœuds et de câbles, three.js dessine l'aperçu 3D dans le navigateur, et rhino3dm lit, sur le serveur, la géométrie Rhino que renvoie Compute. Entre elles circulent des tableaux de nombres, rien de plus.

60 min de lecture et de QCM Prérequis · 31 React et Vite Exemples · graphEditor.jsx, GenericNode.jsx, Viewer3D.jsx, apercu.mjs

L'idée en une phrase

Chaque bibliothèque fait ce qu'elle sait faire, à l'endroit où elle doit le faire : le graphe et la vue 3D dans le navigateur, la géométrie Rhino sur le serveur, à côté de Compute.

L'analogie

Rhino et Grasshopper sur ton poste : le canvas de Grasshopper édite le graphe, la vue de Rhino affiche le résultat, et openNURBS sait ce qu'est un Brep. Magpie rejoue ce partage, réparti entre un serveur et une page web.

À la fin, tu sais

  1. lire le graphe de React Flow : nodes, edges, Handle ;
  2. monter une scène three.js : scène, caméra, rendu ;
  3. dire pourquoi rhino3dm reste sur le serveur ;
  4. suivre un maillage de Compute jusqu'à l'écran.
À retenir Le navigateur ne reçoit jamais de géométrie Rhino. Le serveur la réduit en points, polylignes et maillages, codés en tableaux binaires (Float32Array, Uint32Array), et three.js les envoie tels quels à la carte graphique.

Schéma 1 · React Flow

Le canvas est un état

React Flow ne garde rien pour lui : le graphe, ce sont deux tableaux d'état, nodes et edges, rangés dans useGraphEditor. Chaque geste de l'apprenant devient un changement proposé, que Magpie applique.

graphEditor.jsx · 100–101 et 131–143, condenséconst [nodes, setNodes] = useState([]); const [edges, setEdges] = useState([]); … onNodesChange: useCallback((changes) => setNodes((nds) => applyNodeChanges(changes, nds)), []), onConnect: useCallback((connection) => { setEdges((eds) => addEdge(connection, eds)); clearRuntime(); }, [clearRuntime]),

Proposer, puis appliquer

Glisser un nœud produit des changements (« position de tel id »). applyNodeChanges en tire un nouveau tableau. Un câble posé arrive dans onConnect ; Magpie l'ajoute et efface les teintes du dernier « Tester », qui ne disent plus rien de vrai.

Ton composant pour chaque nœud

nodeTypes = { magpieNode: GenericNode } (ligne 33) : React Flow dessine chaque nœud avec GenericNode. Les poignées sont des <Handle> : type="target" pour une entrée, "source" pour une sortie, id = le nom du port.

Piège courant Écrire nodeTypes à l'intérieur du composant. L'objet serait recréé à chaque rendu, et React Flow croirait à de nouveaux types : nœuds démontés, remontés, état perdu. Magpie le pose une fois, au niveau du module, hors de toute fonction.

Schéma 2 · three.js

Une scène, une caméra, un rendu

three.js dessine avec WebGL, la carte graphique du navigateur. On range des objets dans une scène, on les regarde par une caméra, et le renderer produit l'image dans une balise canvas. Viewer3D monte tout cela une fois, dans un effet.

Viewer3D.jsx · 96–107const camera = new THREE.PerspectiveCamera(40, 1, 0.01, 10000); camera.up.set(0, 0, 1); camera.position.set(12, -18, 12); const controls = new OrbitControls(camera, renderer.domElement); controls.target.set(0, 0, 0); const content = new THREE.Group(); scene.add(content); const render = () => renderer.render(scene, camera); controls.addEventListener("change", render);

Z vers le haut, comme Rhino

three.js tient Y pour la verticale. Magpie redresse la caméra (camera.up.set(0, 0, 1)) et couche la grille dans le plan XY (ligne 88). Axe X rouge, axe Y vert : l'apprenant retrouve les repères de Rhino.

Dessiner sur demande

Pas de boucle à 60 images par seconde : une image est produite quand la caméra bouge, quand le volet change de taille ou quand une réponse arrive. Une vue immobile ne coûte rien, sur un téléphone non plus.

Piège courant Croire que le ramasse-miettes libère la carte graphique. Une géométrie three.js garde ses tampons sur le GPU jusqu'à dispose(). Viewer3D l'appelle sur chaque groupe remplacé (disposeGroup, lignes 63–65) et sur tout le reste quand l'aperçu se ferme (lignes 128–136).

Schéma 3 · rhino3dm

openNURBS dans Node

Compute rend chaque objet Rhino sous forme de texte openNURBS. Pour en tirer des sommets, il faut la bibliothèque de McNeel : rhino3dm, openNURBS compilé en WebAssembly. Magpie ne la charge que sur le serveur, dans apercu.mjs.

apercu.mjs · 187–199function readMesh(rhino, d) { const mesh = rhino.CommonObject.decode(d); if (!(mesh instanceof rhino.Mesh)) { mesh?.delete?.(); return null; } try { const { data } = mesh.toThreejsJSON(); return { positions: data.attributes.position.array, indices: data.index?.array ?? [] }; } finally { mesh.delete(); } }

Chargé une fois, à la demande

rhinoPromise ||= import("rhino3dm").then((m) => m.default()) (ligne 72). Le premier aperçu lance le chargement ; les suivants reçoivent la même promesse. On garde la promesse, pas le module : deux appels simultanés n'en chargent qu'un.

Des tableaux, pas des objets

Chaque nombre part en 4 octets (Float32Array), codé en base64 dans le JSON. Au-delà de 200 000 triangles ou 5 Mo, le serveur arrête d'ajouter et marque l'aperçu truncated : le volet affiche « Aperçu tronqué ».

Piège courant Oublier delete(). Un objet rhino3dm vit dans la mémoire du module WebAssembly, que le ramasse-miettes de JavaScript ne voit pas. Chaque decode de apercu.mjs est suivi d'un delete dans un finally, comme un using en C#.
