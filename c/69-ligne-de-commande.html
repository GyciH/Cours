Le concept

La ligne de commande

La ligne de commande est une façon de lancer des programmes en tapant leur nom et leurs arguments, dans un interpréteur (shell) : cmd ou PowerShell sous Windows, bash sur un serveur Linux. Tout ce que tu y tapes peut s'écrire dans un fichier : c'est un script, qui refait la même chose à chaque fois, sans oubli.

50 min de lecture et de QCM Prérequis · 35 et 46 Exemples · deployer.sh, demarrer_magpie.bat (Magpie), LotATests (SnapSet)

L'idée en une phrase

Un programme reçoit des arguments, des variables d'environnement et une entrée ; il rend une sortie, des erreurs et un code de sortie. Le shell sert à les brancher entre eux.

L'analogie

Une chaîne de montage : chaque poste fait une seule chose, reçoit les pièces du précédent et passe les siennes au suivant, et lève un drapeau rouge s'il échoue. Le script, c'est la fiche qui dit dans quel ordre brancher les postes.

À la fin, tu sais

  1. lire et utiliser un code de sortie ;
  2. séparer stdout et stderr ;
  3. mettre les bons guillemets ;
  4. lancer un programme depuis C#.
À retenir Le code de sortie est la seule réponse qu'un script lit sans effort : 0 veut dire réussi, tout autre nombre veut dire échec. Un outil qui écrit « Erreur » mais sort avec 0 trompe chaque script qui l'appelle.

Schéma 1 · Trois interpréteurs

Mêmes idées, syntaxes différentes

Tes projets mélangent les trois : un .bat pour démarrer Magpie en local, un script sh pour le mettre en ligne, et PowerShell comme terminal par défaut de Windows. Les notions sont les mêmes ; seule l'écriture change.

Exemple autonome · les troisnode script.mjs && echo ok || echo échec # && si 0, || sinon where node # cmd : où est le programme « node » ? Get-Command node # PowerShell command -v node # sh, bash

Le PATH

Quand tu tapes node, le shell cherche un programme de ce nom dans chaque dossier de la variable PATH, dans l'ordre. « Commande introuvable » veut presque toujours dire : installé, mais pas dans le PATH de ce terminal.

Le shebang

La première ligne #!/bin/sh d'un script dit à Linux quel interpréteur l'exécute. Sous Windows, c'est l'extension qui décide : .bat pour cmd, .ps1 pour PowerShell.

Piège courant Un script qui continue après une erreur. Par défaut, sh et cmd passent à la ligne suivante même si la précédente a échoué : on construit puis on déploie un build raté. set -e en sh arrête tout au premier code non nul.

Schéma 2 · Arguments et guillemets

Ce que le programme reçoit vraiment

Avant de lancer le programme, le shell transforme la ligne : il remplace les variables, puis découpe aux espaces. Le programme reçoit une liste d'arguments, sans les guillemets. Les guillemets servent seulement à dire au shell où couper, et quoi remplacer.

Exemple autonome · Node et C#const [, , chemin] = process.argv; // [node, script, 1er argument, …] static int Main(string[] args) // args : déjà découpés, sans guillemets { …; return 0; } // le code de sortie node import-exercise.mjs "D:\Mes exercices\ex.json" // un seul argument

Les chemins avec espaces

Sous Windows, les espaces sont partout : Program Files, Mes exercices. Tout chemin passé en argument se met entre guillemets, dans un script comme dans le code qui fabrique une ligne de commande.

Variables et injection

Une variable non protégée se redécoupe, et ses * se développent en noms de fichiers. Une donnée venue d'ailleurs collée dans une ligne de commande, c'est l'injection du cours 64. On la passe en argument séparé, jamais en texte.

Piège courant Croire que les guillemets arrivent au programme. printf '[%s]' "$x" reçoit deux mots, pas "deux mots". Pour envoyer des guillemets à un autre shell (par ssh, par exemple), il faut deux niveaux : c'est ce que fait deployer.sh, page 5.

Schéma 3 · Tuyaux et redirections

Brancher les programmes entre eux

Chaque programme a trois canaux standard. Le tuyau | relie la sortie de l'un à l'entrée de l'autre, sans fichier intermédiaire ; les redirections envoient un canal dans un fichier. La ligne de mise en ligne de Magpie (cours 35) en est l'exemple parfait.

Exemple autonome · shnpm run build > build.log 2>&1 # tout dans le journal node outil.mjs 2> erreurs.txt # seulement les erreurs grep -c "error" build.log # compter les lignes qui contiennent "error" echo $? # le code de la dernière commande

Pourquoi deux sorties

stdout porte le résultat, que l'on peut rediriger vers un fichier ou un autre programme ; stderr porte les messages pour l'humain, qui restent à l'écran. En Node : console.log écrit sur stdout, console.error sur stderr.

Lancer depuis C#

Process.Start lance un programme ; avec RedirectStandardOutput, le code lit ses sorties ; ExitCode donne son code. C'est ainsi qu'un test de SnapSet exécute le générateur Node du schéma.

Piège courant L'ordre de 2>&1 compte. cmd > f 2>&1 envoie les deux canaux dans f ; cmd 2>&1 > f envoie stderr à l'écran, là où stdout pointait avant la redirection. Les redirections se lisent de gauche à droite.

Glossaire

Shell
Le programme qui lit tes commandes et lance les autres programmes.
Code de sortie
Le nombre rendu par un programme qui se termine : 0 pour réussi.
stdout, stderr
La sortie des résultats et la sortie des messages d'erreur.
PATH
La liste des dossiers où le shell cherche les programmes.
Tuyau
Le lien | qui envoie la sortie d'un programme à l'entrée du suivant.
