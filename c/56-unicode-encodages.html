Le concept

Texte : Unicode, UTF-8 et encodages

Un fichier ne contient pas des lettres mais des octets. Pour retrouver « é », il faut savoir quelle convention a servi à l'écrire. Unicode numérote tous les caractères du monde ; UTF-8 dit comment ranger ces numéros en octets. Se tromper de convention donne « Ã© » à la place des accents.

50 min de lecture et de QCM Prérequis · 01 et 24 Exemples · EcrivainGeneration, ModeleZoneTexte (SnapSet), MagpieSources

L'idée en une phrase

Un caractère a un numéro (son point de code Unicode) et une écriture en octets qui dépend de l'encodage ; lire un fichier, c'est faire le chemin inverse, et il faut connaître l'encodage pour ne pas se tromper de chemin.

L'analogie

Un numéro de téléphone noté sans indicatif. Les chiffres sont justes, mais composés depuis le mauvais pays, ils sonnent chez quelqu'un d'autre. Les octets C3 A9 sont « é » en UTF-8 et « Ã© » en Windows-1252.

À la fin, tu sais

  1. distinguer caractère, point de code et octet ;
  2. dire combien d'octets UTF-8 prend un caractère, et pourquoi ;
  3. reconnaître un mojibake, un � et un BOM mal lu ;
  4. comparer deux chaînes : ordinal, culture, normalisation, fins de ligne.
À retenir Aujourd'hui, la règle simple est : UTF-8 partout, à l'écriture comme à la lecture, et le dire explicitement dans le code. Les ennuis viennent presque toujours d'un endroit qui suppose un autre encodage sans le dire : un vieil outil, Excel, une console Windows.

Schéma 1 · Comment UTF-8 range les numéros

De 1 à 4 octets selon le caractère

UTF-8 garde l'ASCII tel quel (un octet, premier bit à 0). Au-delà, le premier octet annonce la longueur par sa série de 1, et chaque octet suivant commence par 10. Un lecteur qui tombe au milieu d'un caractère le sait donc toujours.

Exemple autonome · C#byte[] b = Encoding.UTF8.GetBytes("é"); // { 0xC3, 0xA9 } string s = Encoding.UTF8.GetString(b); // "é" int n1 = "é".Length; // 1 int n2 = "😀".Length; // 2 : une paire de substitution UTF-16 int n3 = Encoding.UTF8.GetByteCount("😀"); // 4

En mémoire, C# parle UTF-16

Une string .NET est une suite de char de 16 bits. Les caractères au-delà de U+FFFF (emojis, certains idéogrammes) y prennent deux char, une paire de substitution. L'UTF-8 n'intervient qu'à l'entrée et à la sortie.

Le même texte, plusieurs tailles

« Café » fait 4 caractères, 4 char, mais 5 octets en UTF-8. Une limite exprimée en octets (une colonne de base de données, un champ réseau) n'est donc pas une limite en caractères.

Piège courant Length compte des char, pas ce que l'œil voit comme un caractère. Couper une chaîne avec Substring au milieu d'une paire de substitution, ou entre un « e » et son accent combinant, produit un texte invalide ou une lettre sans accent.

Schéma 2 · Trois façons de mal lire

Mojibake, losange et BOM

Chaque symptôme dit quelle erreur a été faite. Des paires bizarres comme « Ã© » : de l'UTF-8 lu dans un encodage d'un octet. Un losange « � » : un octet qui n'est pas de l'UTF-8 valide. « ï»¿ » en tête : la marque d'ordre des octets (BOM) lue comme du texte.

Exemple autonome · C#string a = File.ReadAllText(chemin); // UTF-8, et BOM reconnu s'il y en a un string b = File.ReadAllText(chemin, Encoding.GetEncoding(1252)); // un vieux fichier Windows (.NET Framework) File.WriteAllText(chemin, texte); // UTF-8 sans BOM File.WriteAllText(chemin, texte, new UTF8Encoding(true)); // UTF-8 avec BOM, pour Excel

Le BOM

Les trois octets EF BB BF en tête disent « ceci est de l'UTF-8 ». Utile à certains logiciels, gênant pour d'autres : un JSON ou un script qui commence par un BOM peut être refusé. Le cours 24 en parle à propos des ressources embarquées.

Les anciens encodages

Windows-1252 (proche de Latin-1) range un caractère par octet : é vaut E9. Sous .NET Core et suivants, il faut d'abord enregistrer CodePagesEncodingProvider pour l'utiliser ; sous .NET Framework, il est disponible directement.

Piège courant Excel, sous Windows, ouvre par double-clic un CSV en UTF-8 sans BOM comme un fichier de l'ancien encodage : tous les accents tournent au mojibake. Le même fichier avec BOM s'ouvre bien. Pour un export destiné à Excel, on écrit donc le BOM.

Schéma 3 · Comparer deux textes

Égales pour qui ?

Deux chaînes peuvent s'afficher pareil sans avoir les mêmes char. La comparaison ordinale compare les nombres un à un : rapide et prévisible. La comparaison selon la culture compare comme un lecteur humain d'une langue donnée. La normalisation ramène un texte à une forme unique.

Exemple autonome · C#string.Equals(id1, id2, StringComparison.Ordinal); // identifiants, clés, chemins string.Equals(a, b, StringComparison.OrdinalIgnoreCase); // idem, sans la casse texte.IndexOf(filtre, StringComparison.CurrentCultureIgnoreCase); // recherche pour l'utilisateur string nfc = saisie.Normalize(NormalizationForm.FormC); // « e » + accent → « é »

Ordinal pour la machine

Clés de dictionnaire, identifiants, noms de fichiers, valeurs de schéma : on veut un résultat qui ne change pas selon le PC. On compare en Ordinal ou OrdinalIgnoreCase, et on passe en minuscules avec ToLowerInvariant.

Culture pour l'humain

Une recherche tapée par l'utilisateur, un tri alphabétique affiché : là, la culture compte. Un macOS envoie souvent « é » décomposé (e + accent) ; normaliser en forme C à l'entrée évite deux versions d'un même nom.

Piège courant ToUpper() et ToLower() sans argument suivent la culture du poste. En turc, « i ».ToUpper() donne « İ » (avec un point) : une comparaison de mots-clés qui marchait en France casse en Turquie. D'où les versions …Invariant pour tout ce qui n'est pas affiché.

Glossaire

Point de code
Le numéro d'un caractère dans Unicode, noté U+ suivi de chiffres hexadécimaux.
UTF-8
L'encodage qui écrit chaque point de code sur 1 à 4 octets, ASCII inchangé.
Mojibake
Un texte devenu illisible parce qu'il a été décodé avec le mauvais encodage.
Paire de substitution
Deux char UTF-16 pour un caractère au-delà de U+FFFF.
Normalisation
Ramener un texte Unicode à une forme unique (C : composée, D : décomposée).
