Le concept

Une interface React rapide

React rend une interface en rappelant des fonctions, les composants, chaque fois qu'un état change. Il compare ensuite le nouvel arbre à l'ancien et ne touche le DOM que là où ils diffèrent. Le temps se perd presque toujours avant, dans le JavaScript : trop de composants rappelés, ou un calcul trop cher à chaque rendu.

45 min de lecture et de QCM Prérequis · 31 et 91 Exemples · graphEditor.jsx, GenericNode.jsx, QuickSearch.jsx (Magpie)

L'idée en une phrase

Un rendu évité est le plus rapide de tous ; un rendu inévitable doit être bon marché ; une liste doit dire à React quelle ligne est laquelle.

L'analogie

Un professeur qui relit tout le cahier dès qu'un élève corrige un mot. Il trouve bien la correction, mais il aurait pu ne relire que la page modifiée.

À la fin, tu sais

  1. pourquoi un parent rend tous ses enfants ;
  2. quand memo et useCallback servent ;
  3. choisir la clé d'une liste ;
  4. estimer le coût d'un sélecteur de store.
À retenir Les mesures de ce cours ont été faites avec React 18.3, la version de Magpie, dans Node avec jsdom, en build de production. Le build de développement ajoute des vérifications qui multiplient les durées et faussent les comparaisons.

Schéma 1 · La cascade des rendus

Un parent rend tous ses enfants

Quand l'état d'un composant change, React le rappelle, puis rappelle chacun de ses enfants, sans regarder leurs props. memo ajoute une comparaison : si toutes les props sont identiques (même référence), l'enfant est sauté. Une fonction créée dans le rendu n'est jamais identique à la précédente.

magpie/web/src/graphEditor.jsx · lignes 131 à 139 (extrait)onNodesChange: useCallback((changes) => setNodes((nds) => applyNodeChanges(changes, nds)), []), onEdgesChange: useCallback( (changes) => { setEdges((eds) => applyEdgeChanges(changes, eds)); if (changes.some((c) => c.type === "remove" || c.type === "add")) clearRuntime(); }, [clearRuntime] ),

Une référence stable

useCallback rend la même fonction tant que ses dépendances ne changent pas. Magpie passe ainsi ses gestionnaires à React Flow : le canvas, qui les reçoit en props, ne voit pas une prop neuve à chaque rendu de l'éditeur.

La forme fonctionnelle

setNodes((nds) => …) reçoit l'état courant au lieu de le lire dans la fermeture. Le gestionnaire n'a donc pas besoin de nodes dans ses dépendances : [] suffit, et la fonction ne change jamais.

Piège courant Mettre memo partout sans stabiliser les props. La mesure le montre : 4,41 ms au lieu de 3,45, car memo compare, trouve une fonction neuve, puis rend quand même. Memo et useCallback vont ensemble.

Schéma 2 · Les clés d'une liste

Dire à React qui est qui

Pour une liste, React apparie l'ancienne et la nouvelle ligne qui portent la même key. Une clé stable, l'identifiant de la donnée, lui permet de déplacer ou d'insérer. L'index comme clé fait correspondre les lignes par position : après une insertion en tête, toutes semblent avoir changé.

magpie/web/src/QuickSearch.jsx · lignes 19 à 25const results = useMemo(() => { const q = query.trim().toLowerCase(); if (!q) return []; return catalog .filter((e) => e.name.toLowerCase().includes(q) || (e.displayName || "").toLowerCase().includes(q)) .slice(0, 30); }, [catalog, query]);

Le calcul mis de côté

useMemo ne refait le filtre que si catalog ou query changent. Et slice(0, 30) borne le nombre de lignes rendues, quelle que soit la taille du catalogue : le moyen le plus sûr de rendre une liste vite est d'en rendre peu.

Les clés de Magpie

Le ruban rend ses icônes avec key={entry.typeGuid} (CategoryRibbon.jsx:154), un identifiant stable. La grille utilise key={i} (GridList.jsx:59) : acceptable ici, car le brouillon d'une ligne est relu depuis sa valeur au double-clic (ligne 36).

Piège courant Prendre l'index pour clé dans une liste où l'on insère, supprime ou trie, et dont les lignes gardent un état. L'état reste à sa position : la nouvelle ligne hérite de l'état de l'ancienne première, sans erreur visible.

Schéma 3 · Le sélecteur de store

S'abonner à une petite partie

React Flow garde nœuds et câbles dans un store. useStore(sélecteur) abonne un composant à ce que rend le sélecteur : à chaque mise à jour du store, React Flow rappelle tous les sélecteurs, et ne rend que les composants dont la valeur a changé.

magpie/web/src/GenericNode.jsx · lignes 43 à 49const connectedKey = useStore((st) => st.edges .filter((e) => e.target === id) .map((e) => e.targetHandle) .sort() .join("|") );

Pourquoi une chaîne

Le store compare l'ancienne et la nouvelle valeur par ===. Un tableau construit à chaque appel serait toujours différent et ferait rendre le nœud à chaque mise à jour. Une chaîne triée est égale tant que les câbles du nœud sont les mêmes : le rendu est évité.

Le coût qui reste

Éviter le rendu n'évite pas l'appel : chaque nœud parcourt tous les câbles à chaque mise à jour, déplacement compris. Un index des câbles par nœud cible, calculé une fois par mise à jour, ramènerait chaque sélecteur à une simple lecture.

Piège courant Écrire nodeTypes dans le corps du composant. Un objet neuf à chaque rendu fait recréer tous les nœuds par React Flow. Magpie le déclare hors du composant (graphEditor.jsx:33), une fois pour toutes.

Glossaire

Rendu
L'appel d'un composant, qui renvoie l'arbre qu'il veut afficher.
Réconciliation
La comparaison de l'ancien et du nouvel arbre.
Validation (commit)
L'application des différences au DOM.
Référence stable
Une valeur qui reste === d'un rendu à l'autre.
Sélecteur
Une fonction qui extrait d'un store la partie qu'un composant affiche.
