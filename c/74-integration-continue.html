Le concept

L'intégration continue

Tes vérifications existent déjà : construire sans avertissement, lancer les tests. L'intégration continue (CI) les confie à une machine, qui les rejoue à chaque envoi de code, sur un système neuf, et affiche le verdict à côté du commit. Ce n'est pas un outil de plus : c'est ta liste de contrôle, rendue automatique et impossible à oublier.

50 min de lecture et de QCM Prérequis · 06, 69 et 73 Exemples · tests de web/ (Magpie), ResolutionTests (SnapSet), Cuttlefish.csproj

L'idée en une phrase

Une recette écrite dans le dépôt dit comment installer, compiler et tester ; un service l'exécute sur une machine vierge à chaque push ou pull request, et refuse de passer au vert si une seule étape échoue.

L'analogie

Le contrôle technique d'une voiture. Le garagiste n'a jamais vu la voiture, il suit une grille fixe, et il ne croit pas le propriétaire sur parole : seul compte ce que la grille mesure ce jour-là.

À la fin, tu sais

  1. dire ce qu'une machine neuve révèle ;
  2. lire un workflow GitHub Actions ;
  3. rendre un projet constructible ailleurs ;
  4. réagir à un verdict rouge.
À retenir « Intégration » parce que chaque changement est fusionné tôt et souvent dans la branche commune ; « continue » parce que la vérification suit chaque envoi, et pas une grande séance avant la livraison. Plus un problème est vu tôt, moins il coûte : on sait encore quel changement l'a causé.

Schéma 1 · Ce que révèle une machine neuve

« Ça marche chez moi »

Ton poste accumule des choses que le dépôt ne contient pas : des paquets déjà installés, un Rhino dans un dossier précis, des variables d'environnement, des fichiers générés hier. Une machine neuve n'a que le dépôt. L'expérience ci-dessous a été faite sur une copie du dossier web/ de Magpie.

Exemple autonome · terminal, l'expérience reproduitecp -r web /tmp/essai && cd /tmp/essai # sans node_modules npm test # 22 réussis, 3 échecs : rhino3dm introuvable npm ci # installe le verrou (cours 73) npm test # 25 réussis

Reproductible

Une CI n'a de valeur que si son résultat ne dépend que du commit. D'où npm ci plutôt que npm install, des versions figées, et aucun accès à un fichier de ton poste.

Rapide

Une vérification qui prend une heure ne sera pas attendue. Les 25 tests du canevas tournent en 0,3 s et la construction Vite en 5 s (mesurés) : une CI de ce dossier rendrait son verdict en moins d'une minute.

Piège courant Un test qui dépend de l'ordre ou de l'heure : il passe 49 fois sur 50. Un tel test « instable » apprend vite à tout le monde à ignorer le rouge, et la CI ne sert plus à rien. On le corrige ou on le rend déterministe, on ne le relance pas jusqu'au vert.

Schéma 2 · Un workflow GitHub Actions

La recette, versionnée avec le code

Sur GitHub, la CI s'appelle Actions. Un fichier YAML placé dans .github/workflows/ décrit quand se lancer, sur quelle machine, et quelles étapes enchaîner. Aucun de tes trois dépôts n'en a encore : l'exemple est donc autonome, écrit pour le dossier web/ de Magpie.

Exemple autonome · .github/workflows/web.ymlon: [push, pull_request] jobs: tests: runs-on: ubuntu-latest defaults: { run: { working-directory: web } } steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: { node-version: 24 } - run: npm ci - run: npm test - run: npm run build

uses et run

run lance une commande, comme dans un terminal. uses appelle une action toute faite, publiée par quelqu'un d'autre et versionnée (@v4) : c'est une dépendance, à choisir comme un paquet npm.

Les secrets

Une étape qui déploie a besoin d'une clé. Elle se range dans les réglages du dépôt et se lit par ${{ secrets.NOM }} ; elle n'apparaît ni dans le YAML ni dans les journaux (cours 63).

Piège courant Lancer la CI sur une pull request venue d'un inconnu avec accès aux secrets. Son code s'exécute sur la machine de CI : il peut lire tout ce qu'on lui confie. GitHub retient par défaut les secrets pour les pull requests issues d'un fork ; ne pas contourner ce garde-fou.

Schéma 3 · Construire sans Rhino

Ce que la machine de CI ne peut pas avoir

Une machine de CI ne contient pas Rhino : il ne s'y installe pas en une ligne, et il demande une licence. Compiler un plugin Grasshopper y reste possible ; l'exécuter dans Rhino, non. Tes dépôts montrent les deux manières de référencer Grasshopper.

Exemple autonome · séparer les tests qui ont besoin de Rhino (xUnit)[Fact, Trait("Besoin", "Rhino")] public void LeCodeEmisCompile() { … } dotnet test --filter "Besoin!=Rhino" // en CI dotnet test // sur le poste, tout

Une CI Windows

Les projets SnapSet visent net7.0-windows et WinForms : ils se construisent sur un runner windows-latest. Le changement d'étiquette suffit, mais la machine Windows est plus lente à démarrer.

Ce qui reste à la main

Le rendu sur le canvas, les gestes, l'apparence d'une capsule : README.md:88–89 de SnapSet le dit, ils se vérifient dans Rhino. La CI ne remplace pas ce passage, elle évite d'y arriver avec un code qui ne compile pas.

Piège courant Désactiver un test qui échoue en CI « parce qu'il passe chez moi ». La différence entre les deux machines est justement l'information : un chemin figé, un fichier oublié dans le dépôt, une version différente. On la trouve avant de toucher au test.

Glossaire

Intégration continue
Rejouer construction et tests à chaque envoi, sur une machine neuve.
Workflow
Le fichier YAML qui décrit quand et comment la CI travaille.
Runner
La machine, souvent jetable, qui exécute un job.
Test instable
Un test dont le verdict change sans que le code change.
Reproductible
Qui donne le même résultat à partir du même commit, où qu'on le lance.
