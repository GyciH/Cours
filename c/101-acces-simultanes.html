Le concept

Les accès simultanés

Le serveur de Magpie garde magpie.db ouverte pendant qu'il tourne. Un script lancé en SSH, ou un outil de consultation, peut ouvrir le même fichier au même moment. SQLite n'a pas de serveur pour arbitrer : chaque connexion pose des verrous sur le fichier, et celle qui trouve la place prise attend ou échoue.

45 min de lecture et de QCM Prérequis · 67 et 100 Exemples · db.mjs, restore-authorized.mjs, README.md (Magpie)

L'idée en une phrase

Plusieurs lecteurs, un seul écrivain à la fois ; le journal choisit si les lecteurs doivent parfois attendre, et le délai d'attente si l'on échoue tout de suite.

L'analogie

Un tableau d'affichage : tout le monde peut le lire, une seule personne à la fois peut le modifier. En mode delete, elle masque le tableau le temps de recoller l'affiche ; en WAL, elle prépare l'affiche à côté.

À la fin, tu sais

  1. dire qui bloque qui ;
  2. choisir entre les journaux delete et WAL ;
  3. régler un délai d'attente ;
  4. éviter qu'un lecteur voie un état à moitié écrit.
À retenir Le cours 67 parlait des fils d'un même processus. Ici, ce sont des processus séparés, qui ne partagent que le fichier. Les mesures ont été faites avec deux processus Node réels, ouverts sur le même fichier.

Schéma 1 · Les verrous

Qui bloque qui

Une connexion qui veut écrire réserve la base : une seule peut le faire à la fois. Ce que les lecteurs subissent dépend du journal. En mode delete, l'écrivain modifie le fichier lui-même et doit en écarter les lecteurs pendant ce temps. En mode WAL, il écrit ses changements dans un fichier à part, et les lecteurs continuent sur l'ancien état.

magpie/web/db.mjs · lignes 13 et 14export function openDb() { const db = new DatabaseSync(DB_PATH);

Write-Ahead Log

En WAL, un validateur ajoute ses pages au fichier magpie.db-wal ; les lecteurs lisent la base plus ce journal jusqu'au point où ils ont commencé. Les pages sont recopiées dans la base plus tard, par paquets. Deux fichiers de plus apparaissent à côté : -wal et -shm.

Les réglages de Magpie

openDb ouvre la base sans option et n'exécute aucun PRAGMA journal_mode : magpie.db est donc en journal delete, avec un délai d'attente nul. Rien, dans db.mjs, ne parle d'accès simultanés.

Piège courant Copier seulement magpie.db d'une base en mode WAL. Les dernières validations peuvent encore se trouver dans -wal : la copie est en retard, voire incohérente (cours 102).

Schéma 2 · Le délai d'attente

Attendre plutôt qu'échouer

Quand le verrou est pris, SQLite peut réessayer un moment avant d'abandonner. Ce délai d'attente (busy timeout) vaut 0 par défaut dans node:sqlite : la moindre rencontre rend aussitôt l'erreur database is locked. Une valeur de quelques secondes transforme la plupart des conflits en courtes attentes.

Exemple autonome · node:sqlite, ouvrir une base partagéeconst db = new DatabaseSync(DB_PATH, { timeout: 5000 }); // attendre jusqu'à 5 s db.exec("PRAGMA journal_mode = WAL"); // les lecteurs ne sont plus écartés

Le serveur, une seule connexion

compute-proxy.mjs ouvre la base une fois (ligne 100) et Node exécute une requête à la fois : à l'intérieur du serveur, aucun conflit n'est possible. Les conflits viennent d'un autre processus, un script ou un second serveur.

Ce que voit l'utilisateur

Une écriture refusée lève une exception dans le gestionnaire de la route. Le serveur répond alors par une erreur, et l'administrateur voit son action échouer sans raison apparente. Déduit du code, non provoqué.

Piège courant Mettre un délai très long pour ne plus jamais voir l'erreur. Une transaction oubliée ouverte bloquerait alors tous les écrivains pendant tout le délai ; l'erreur, elle, au moins se voit.

Schéma 3 · L'isolation

Ne jamais montrer une moitié

L'isolation, le I de ACID, promet qu'un lecteur ne voit jamais une transaction inachevée. Mais si chaque instruction est sa propre transaction, les étapes intermédiaires sont, chacune, des états validés : rien n'empêche un lecteur de les voir.

magpie/web/restore-authorized.mjs · lignes 38 à 43// Remise à zéro : l'état final doit refléter EXACTEMENT le seed, sans conserver // d'autorisations faites entre-temps — sinon « restaurer » ne restaurerait rien. const avant = db.prepare("SELECT COUNT(*) n FROM components WHERE isAuthorized = 1").get().n; db.prepare("UPDATE components SET isAuthorized = 0").run(); const activer = db.prepare("UPDATE components SET isAuthorized = 1 WHERE typeGuid = ?");

Un ruban vide, un instant

Entre la remise à zéro et la dernière activation, le catalogue autorisé est incomplet. Un apprenant qui charge la page à ce moment reçoit un ruban avec moins de composants, voire aucun. La fenêtre dure quelques millisecondes par composant.

BEGIN IMMEDIATE

IMMEDIATE prend le verrou d'écriture dès le BEGIN, au lieu d'attendre la première écriture. Une transaction qui lit puis écrit ne risque plus d'être refusée au milieu, après avoir lu un état qu'un autre aurait changé.

Piège courant Conclure d'un essai réussi qu'il n'y a pas de problème. La mesure ne l'a montré que dans deux essais sur cinq, une seule lecture à chaque fois : c'est un défaut rare, qu'on prévient par construction.

Glossaire

Verrou de fichier
Une réservation posée sur la base pour écarter les autres connexions.
WAL
Write-Ahead Log : un journal où l'on ajoute les changements avant de les recopier.
Délai d'attente
Le temps pendant lequel SQLite réessaie avant de rendre « database is locked ».
Isolation
La garantie qu'un lecteur ne voit pas une transaction inachevée.
Connexion
Un accès ouvert à la base, avec ses verrous et ses transactions.
