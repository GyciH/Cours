Le concept

Le backend qui parle
à Rhino Compute

Rhino Compute, c'est Rhino et Grasshopper sans fenêtre, derrière une adresse HTTP. Le backend de Magpie lui envoie une définition .ghx fabriquée à partir du canvas, lit ce qui revient, et décide seul du verdict. Le navigateur, lui, n'est jamais cru sur parole.

60 min de lecture et de QCM Prérequis · 24, 30 et 32 Exemples · compute-proxy.mjs, computeOutputs.mjs, serializer/

L'idée en une phrase

Le backend traduit le graphe en .ghx, entoure de groupes RH_OUT: ce qu'il veut récupérer, et Compute lui rend exactement ces sorties-là, en JSON.

L'analogie

Envoyer un .gh à un collègue qui a Rhino ouvert, avec une consigne : « renvoie-moi seulement ce qui est dans le groupe Réponse ». Il calcule, recopie ce groupe, et ne sait rien de l'exercice. Le jugement reste chez toi.

À la fin, tu sais

  1. suivre une soumission, du clic au verdict ;
  2. dire comment un graphe devient un .ghx ;
  3. lire la requête /grasshopper et sa réponse ;
  4. nommer les gardes qui protègent le serveur.
À retenir Compute ne connaît ni les exercices ni les apprenants : il calcule ce qu'on lui envoie. Tout ce qui touche à la confiance (composants permis, objets du départ, verdict) se décide dans compute-proxy.mjs, avant et après l'appel.

Schéma 1 · Du graphe au .ghx

Des nœuds JSON aux chunks GH_IO

Le cours 24 a montré le format .ghx : des chunks et des items typés. Le backend en écrit un de toutes pièces, sans Rhino, avec trois modules de src/serializer/, puis le code en base64.

compute-proxy.mjs · 433–442function generateGhx(nodes, edges, groups = [], catalogByGuid = …, guidsOut = null) { const defObjects = buildDefinitionObjectsChunk(nodes, edges, catalogByGuid, groups, guidsOut); const skeleton = buildDefinitionChunkSkeleton("magpie_exercise.ghx"); const definitionChunk = chunk("Definition", skeleton.itemsPluginVersion, [...skeleton.childChunks, defObjects]); return serializeArchive([definitionChunk], buildRootItems()); } function toBase64Utf8(str) { return Buffer.from(str, "utf-8").toString("base64"); }

Le câble devient une Source

Dans un .ghx, un câble n'est pas un objet. Le port d'entrée retient le GUID de la sortie qui l'alimente : un item Source par câble, puis SourceCount (build-graph.mjs, lignes 132–135).

Un groupe pour dire quoi rendre

Compute renvoie la sortie de chaque groupe dont le nom commence par RH_OUT:. Pour une soumission, le backend entoure le composant câblé au marqueur Réponse d'un groupe RH_OUT:answer (computeOutputs.mjs, ligne 7).

Piège courant Chercher RH_OUT:answer quand le composant a plusieurs sorties. Compute ajoute alors le surnom de la sortie : RH_OUT:answer (S). outputParamCandidates essaie d'abord ce nom suffixé, puis le nom nu (computeOutputs.mjs, lignes 28–30).

Schéma 2 · La requête et la réponse

Un POST, un arbre en retour

Un seul point d'entrée : POST /grasshopper. Le corps porte la définition ; la réponse porte une entrée par groupe RH_OUT:, avec ses données rangées en arbre, comme dans Grasshopper.

computeOutputs.mjs · 38–58, condenséexport function extractOutputTree(computeResponse, candidates) { for (const candidate of candidates) { const entry = computeResponse.values?.find((v) => v.ParamName === candidate); if (!entry?.InnerTree) continue; const tree = {}; for (const path of Object.keys(entry.InnerTree)) { tree[path] = entry.InnerTree[path].map((item) => { try { return JSON.parse(item.data); } catch { return item.data; } }); } return { tree, paramName: candidate }; } …

Du JSON dans du JSON

Chaque item.data est une chaîne qui contient du JSON : "3.5", ou "\"abc\"" pour un texte. D'où le JSON.parse par item, et la donnée brute si le décodage échoue.

Les chemins de l'arbre

Les clés {0}, {0;1} sont les chemins de branches de Grasshopper. Pour comparer à la réponse attendue, flattenTree met les branches bout à bout, dans l'ordre reçu (ligne 61).

Piège courant Prendre un 500 de Compute pour une panne. Compute répond 500 dès qu'un composant est en erreur (une division par zéro), alors que le calcul a abouti. Pour « Tester », Magpie renvoie 200 avec les messages, et le composant se teinte en rouge (compute-proxy.mjs, lignes 581–585).

Schéma 3 · Ne jamais croire le navigateur

Cinq gardes autour de Compute

Tout ce qui arrive du navigateur a pu être modifié : il suffit des outils de développement. Le backend vérifie donc lui-même ce que l'interface semble déjà garantir.

compute-proxy.mjs · 149–160, condenséfunction assertAuthorizedGraph(nodes) { const rows = db.prepare("SELECT typeGuid FROM components WHERE isAuthorized = 1").all(); const allowed = new Set(rows.map((r) => r.typeGuid)); allowed.add(PANEL_GUID); const refused = [...new Set(nodes.filter((n) => !n?.opaque) .map((n) => n?.typeGuid).filter((guid) => !allowed.has(guid)))]; if (refused.length > 0) throw new HttpError(400, `Composant(s) non autorisé(s) : …`, "UNAUTHORIZED_COMPONENT"); }

Le ruban ne suffit pas

Masquer un composant du ruban est un confort, pas une protection. Sans ce contrôle, un client modifié pourrait envoyer n'importe quel GUID connu, y compris le comparateur réservé à la correction (commentaire des lignes 146–148).

Le verdict muet

sendVerdict écrit la raison dans le journal du serveur et ne renvoie que { status, pass } (lignes 360–364). Comme dans le plugin, l'apprenant ne sait pas pendant le parcours pourquoi une réponse est fausse.

Piège courant Comparer un mot de passe avec ===. La comparaison s'arrête au premier caractère faux, et le temps de réponse trahit le secret petit à petit. sameSecret compare deux empreintes SHA-256 avec timingSafeEqual, qui prend toujours le même temps (lignes 460–462).
