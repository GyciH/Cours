Le concept

Fusionner et rebaser

Une branche finit par revenir dans la ligne principale. Git sait le faire de deux manières : la fusion ajoute un commit qui réunit les deux histoires, le rebasage rejoue les commits de la branche au bout de l'autre, comme s'ils avaient été écrits après. Le code obtenu est le même ; l'histoire racontée ne l'est pas.

45 min de lecture et de QCM Prérequis · 103 et 104 Exemples · l'histoire de Magpie, un dépôt d'essai

L'idée en une phrase

Fusionner garde l'histoire telle qu'elle s'est passée ; rebaser la réécrit pour qu'elle se lise en ligne droite ; écraser la résume en un seul commit.

L'analogie

Deux rédacteurs d'un même rapport. On peut agrafer leurs deux chapitres avec une note « réunis le 22/10 », recopier le second à la suite du premier comme s'il était venu après, ou réécrire les deux en un seul chapitre.

À la fin, tu sais

  1. prévoir l'histoire que laisse chaque méthode ;
  2. reconnaître une avance rapide ;
  3. savoir quand ne pas rebaser ;
  4. lire une histoire faite de fusions.
À retenir Les trois méthodes ont été jouées sur la même situation, dans un dépôt d'essai aux dates fixées : les identifiants cités dans ce cours sont réels et reproductibles.

Schéma 1 · La fusion

Un commit à deux parents

Git cherche l'ancêtre commun des deux branches, compare chacune à lui, et combine les deux séries de changements. Le résultat est rangé dans un commit de fusion, le seul genre de commit à avoir deux parents. Rien de ce qui existait n'est modifié.

Exemple autonome · Git, les deux fusions possiblesgit switch main git merge f # avance rapide si main n'a pas bougé, sinon commit de fusion git merge --no-ff f # toujours un commit de fusion

Le premier parent

Le premier parent d'une fusion est la branche où l'on était, le second celle qu'on a réunie. git log --first-parent ne suit que le premier : sur Magpie, 56 lignes au lieu de 134, une par pull request ou commit direct.

Pourquoi forcer --no-ff

Une avance rapide ne laisse aucune trace que la branche a existé. Le commit de fusion, lui, garde le nom de la pull request et le moment de son intégration ; on peut l'annuler d'un seul geste.

Piège courant Faire git pull par réflexe sur une branche où l'on a committé. Si la branche distante a aussi avancé, Git crée une fusion locale sans intérêt ; git pull --rebase rejoue plutôt ses commits au bout.

Schéma 2 · Le rebasage

Rejouer au bout

git rebase main prend les commits propres à la branche, les retire, avance la branche au bout de main, puis applique de nouveau chaque changement, un par un. Chaque commit rejoué est un nouveau commit, avec un nouveau parent et donc un nouvel identifiant.

Exemple autonome · Git, rebaser puis intégrergit switch f git rebase main # f1', f2', f3' au bout de main git switch main git merge --ff-only f # avance rapide, refusée si elle n'est pas possible

Un conflit par commit

Une fusion rencontre au plus un conflit par fichier, une fois. Un rebasage rejoue les commits un à un et peut s'arrêter sur chacun : git rebase --continue après chaque résolution, --abort pour tout annuler (cours 106).

Rebaser pour nettoyer

git rebase -i ouvre la liste des commits à rejouer : on peut les réordonner, renommer, fusionner ou supprimer avant de les partager. C'est le seul moment où réécrire est sans danger.

Piège courant Rebaser une branche déjà poussée et suivie par d'autres. Leurs copies gardent f1, f2, f3 ; la tienne a f1', f2', f3' : au prochain échange, chaque changement apparaît en double. On ne rebase que ce qu'on est seul à avoir.

Schéma 3 · Choisir

Trois histoires pour le même code

La troisième méthode, l'écrasement (squash), applique tous les changements de la branche en un seul commit ordinaire, sans lien avec les commits d'origine. Le choix entre les trois dépend de ce qu'on veut lire plus tard dans l'histoire.

Exemple autonome · Git, l'écrasementgit switch main git merge --squash f # « Squash commit -- not updating HEAD » git commit -m "f (écrasé)" # un seul commit, un seul parent

Fusion, pour garder le contexte

Utile quand les commits d'une branche racontent chacun une étape qu'on voudra retrouver, et qu'on veut savoir quand l'ensemble a été intégré. C'est le choix de Magpie.

Écrasement, pour un sujet par commit

Utile quand une branche contient des essais (« wip », « correction », « encore ») qu'on ne veut pas garder : main reçoit un commit par fonctionnalité, facile à annuler. Les étapes détaillées restent dans la pull request.

Piège courant Continuer à travailler sur une branche écrasée dans main. Ses anciens commits n'y sont pas, Git ne voit pas qu'ils ont été intégrés : la fusion suivante rejoue tout et produit des conflits sur du code déjà là.

Dans tes projets

L'histoire de Magpie, faite de fusions

Magpie intègre chaque pull request par un commit de fusion, qui reprend le nom de la branche et le titre de la PR. Les branches, elles, restent sur GitHub après la fusion.

À surveiller · quatorze branches fusionnées jamais supprimées Sur GitHub, Magpie garde 14 branches de pull request (Admin-react, Apercu-3D, Versions-plugin…) dont chaque commit est déjà dans master. Elles ne coûtent rien, mais la liste des branches ne dit plus ce qui est en cours, et une branche réutilisée par erreur repartirait d'un état ancien. Le réglage « Automatically delete head branches » du dépôt les supprime à chaque fusion ; les commits restent dans master. Relevé par git ls-remote et merge-base, sans rien modifier.

Glossaire

Fusion (merge)
La réunion de deux histoires dans un commit à deux parents.
Avance rapide
Une fusion où la branche n'a qu'à avancer, sans nouveau commit.
Rebasage (rebase)
Le fait de rejouer des commits au bout d'une autre branche.
Écrasement (squash)
La réunion de plusieurs commits en un seul.
Premier parent
Le parent d'une fusion qui vient de la branche où l'on était.
