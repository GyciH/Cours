Le concept

Chercher dans l'histoire

L'histoire d'un dépôt est une base de données : chaque version de chaque ligne y est, datée et signée. Git fournit quatre manières de l'interroger, selon qu'on cherche un texte, une ligne, un passage, ou le moment où quelque chose a cessé de marcher.

45 min de lecture et de QCM Prérequis · 103 à 107 Exemples · Magpie, SnapSet, un dépôt d'essai

L'idée en une phrase

Chercher dans l'histoire, c'est poser une question précise (quel texte, quelle ligne, quel test) plutôt que de lire des centaines de commits.

L'analogie

Un cahier de chantier tenu au jour le jour. On peut chercher le jour où un mot apparaît, demander qui a écrit tel paragraphe, ou, pour trouver le jour où la fissure est apparue, ouvrir au milieu, puis au milieu de la bonne moitié.

À la fin, tu sais

  1. choisir entre -S et -G ;
  2. ne pas croire blame sur parole ;
  3. suivre un fichier renommé ;
  4. automatiser une bisection.
À retenir Ces recherches ne valent que si les commits sont petits et bien nommés. Un commit « divers » de 2 000 lignes répond à toutes les questions par « là, quelque part » : c'est le meilleur argument pour des commits courts.

Schéma 1 · La pioche

Trouver quand un texte a changé

git log -S texte, surnommé la pioche (pickaxe), ne lit pas les messages : il compare, pour chaque commit, combien de fois le texte apparaît avant et après. -G motif cherche une expression régulière dans les lignes ajoutées ou retirées du diff. Les deux ne trouvent pas les mêmes commits.

Exemple autonome · Git, chercher un textegit log -S CheckTextList --oneline # apparitions et disparitions git log -G 'Marge\s*=' -p -- schema/ # lignes modifiées, avec le diff git log --grep=revert -i # dans les messages, pas le code git grep -n Marge v0.1.0 # dans une version donnée

-S pour un nom

Pour savoir quand une fonction, une classe ou une constante est née ou morte, -S est exact : il ne s'arrête que sur les commits qui changent son nombre d'apparitions, pas sur ceux qui l'utilisent.

-G pour une valeur

Pour suivre les changements d'une ligne dont le nom reste (une valeur, un réglage), -G voit chaque modification. Il trouve aussi plus de bruit : toute ligne du diff qui correspond.

Piège courant Chercher par --grep ce qu'il fallait chercher par -S. --grep ne lit que les messages : si le commit qui a introduit un défaut ne le nomme pas, et c'est presque toujours le cas, il ne sort pas.

Schéma 2 · L'auteur d'une ligne

blame, et ce qu'il ne voit pas

git blame annote chaque ligne du fichier actuel avec le dernier commit qui l'a modifiée. Quand une ligne a été déplacée ou recopiée d'un autre fichier, ce dernier commit est le déplacement, pas l'écriture. Les options -C lui demandent de chercher plus loin.

Exemple autonome · Git, interroger une lignegit blame -L 30,36 f # une plage seulement git blame -w -C -C -C f # ignorer les espaces, suivre les copies git log -L 30,36:f # chaque version de la plage, avec le diff git log --follow -- f # l'histoire à travers les renommages

Un, deux, trois -C

Un -C cherche les lignes venues d'autres fichiers modifiés dans le même commit, deux dans le commit qui a créé le fichier, trois dans tous les commits. Une ligne doit dépasser environ 40 caractères pour être reconnue, d'où l'échec sur la ligne seule.

log -L, l'histoire d'un passage

Là où blame donne une date par ligne, git log -L montre chaque commit qui a touché la plage, avec son diff. Sur Metrique.cs de SnapSet, la ligne 1980 n'a qu'un commit : l'état initial du 07/10.

Piège courant Conclure « c'est lui qui a écrit ça » d'après blame. Un reformatage, un déplacement, une scission de fichier mettent leur auteur sur des lignes qu'il n'a pas pensées : c'est le cas des 62 lignes de Directory.Build.props.

Schéma 3 · La bisection

Trouver le commit qui a tout cassé

On connaît un commit bon et un commit mauvais. git bisect se place au milieu, demande si c'est bon ou mauvais, garde la moitié suspecte, et recommence. Avec un script qui répond à la place, la recherche est entièrement automatique.

Exemple autonome · Git, une bisection automatiquegit bisect start HEAD v0.1.0 # mauvais, puis bon git bisect run ./test.sh # 0 bon, 1 mauvais, 125 à sauter git bisect log # la trace, rejouable git bisect reset # retour à la branche de départ

Un test qui ne dépend que du commit

Le script doit répondre pour le commit sorti, sans dépendre de fichiers non suivis. Pour un plugin, c'est souvent « compile-t-il » ou un test unitaire ; ici, un git ls-files suffit.

Les fusions

Bisect explore aussi les branches fusionnées : le premier commit testé sur Magpie était la fusion de la PR #35 (168460f). --first-parent limite la recherche à la ligne principale.

Piège courant Oublier git bisect reset. Le dépôt reste sur un commit ancien, HEAD détachée : le travail fait ensuite n'est sur aucune branche (cours 104).

Glossaire

Pioche (pickaxe)
La recherche par -S, qui compte les apparitions d'un texte.
Blame
L'annotation de chaque ligne par le dernier commit qui l'a touchée.
Bisection
La recherche par moitiés du premier commit fautif.
Renommage
Un fichier supprimé et recréé, reconnu par sa ressemblance (R096).
Plage
Un groupe de lignes désigné par -L début,fin.
