Le concept

Les objets de Git

Sous les commandes, Git est une petite base de données d'objets. Il n'en connaît que trois sortes utiles : le blob (le contenu d'un fichier), l'arbre (un dossier) et le commit (une photo datée de l'arbre racine). Chaque objet est nommé par l'empreinte de son contenu. Tout le reste, branches et historique, s'en déduit.

45 min de lecture et de QCM Prérequis · 06 et 65 Exemples · le dépôt SnapSet, lu par git cat-file (copie de travail)

L'idée en une phrase

Un commit pointe vers un arbre et vers son parent ; un arbre pointe vers des blobs et d'autres arbres ; chaque nom est l'empreinte de ce qu'il désigne.

L'analogie

Une bibliothèque où chaque livre est classé sous un numéro calculé à partir de son texte. Deux exemplaires identiques reçoivent le même numéro et ne prennent qu'une place ; corriger une virgule donne un autre livre.

À la fin, tu sais

  1. lire un commit, un arbre, un blob ;
  2. dire d'où vient un identifiant ;
  3. expliquer pourquoi l'historique pèse peu ;
  4. prévoir ce que change une réécriture.
À retenir Tout ce cours a été mesuré sur une copie du dépôt SnapSet, faite pour l'occasion : le dépôt d'origine n'a été que lu. Les expériences qui modifient l'histoire ont été faites dans un dépôt d'essai de quatre commits.

Schéma 1 · Nommé par son contenu

L'identifiant est une empreinte

Git calcule le SHA-1 (cours 65) d'un petit en-tête, le type et la taille, suivi du contenu. Les 40 chiffres hexadécimaux obtenus servent de nom : on parle de stockage adressé par le contenu. Un fichier n'a pas d'identifiant à lui ; c'est son contenu qui en a un.

Exemple autonome · Python, recalculer l'identifiant d'un blobimport hashlib, subprocess b = subprocess.run(["git", "cat-file", "blob", "HEAD:README.md"], capture_output=True).stdout print(hashlib.sha1(b"blob %d\0" % len(b) + b).hexdigest()) # 8dd1f8f227ecc828e5544d4163c551effb31855b (comme git rev-parse HEAD:README.md)

Le nom n'est pas dans le blob

Un blob ne contient que des octets : ni nom de fichier, ni droits, ni date. Le nom vit dans l'arbre qui le cite. Renommer un fichier sans le modifier crée donc un nouvel arbre, mais garde le même blob.

Et SHA-256 ?

SHA-1 n'est plus sûr contre une attaque préparée (cours 65). Git sait détecter les collisions connues, et propose des dépôts en SHA-256 depuis 2020 ; les dépôts de GitHub restent en SHA-1, pour longtemps encore.

Piège courant Croire que Git range des différences entre versions. Il range des contenus entiers, un blob par version ; les différences n'apparaissent qu'à l'affichage, et, pour gagner de la place, dans les paquets.

Schéma 2 · Les paquets

Toute l'histoire pèse moins qu'une copie

Un objet neuf est d'abord écrit seul, compressé, dans .git/objects. Puis Git regroupe les objets en paquets, où une version proche d'une autre n'est rangée que comme une liste de différences, un delta. Le stockage reste celui de contenus entiers ; le paquet n'est qu'une façon compacte de les écrire.

Exemple autonome · Git, ce que pèse chaque type d'objet dans un dépôtgit cat-file --batch-all-objects --batch-check="%(objecttype) %(objectsize) %(objectsize:disk)" git count-objects -vH # size-pack: 1.10 MiB pour SnapSet

Un gros fichier souvent modifié

schema/Metrique.cs fait 3 366 lignes et 180 Ko. Douze versions, 2 Mo en tout, occupent 68 Ko dans le paquet : chaque modification ne change que quelques lignes, et seul ce changement est rangé.

Ce qui ne se compresse pas

Une image, une DLL, un fichier .gh changent presque entièrement d'une version à l'autre : aucun delta utile. Dix versions d'une image de 5 Mo pèsent près de 50 Mo pour toujours, même après la suppression du fichier.

Piège courant Supprimer un gros fichier par un nouveau commit pour alléger le dépôt. Les commits précédents le citent toujours : il reste dans chaque clone. Seule une réécriture de toute l'histoire l'en retire.

Schéma 3 · Immuable

Changer un commit, c'est en créer d'autres

Un commit contient l'identifiant de son parent. Changer quoi que ce soit dans un commit, même son message, change son empreinte ; ses enfants, qui la citent, doivent alors être recréés, et ainsi de suite jusqu'au bout de la branche. Aucun objet n'est jamais modifié : on en écrit de nouveaux.

Exemple autonome · le dépôt d'essai, c4 avant et après, git cat-file -ptree 0fbef63bfc8b58a623b154a2903d54d51eeccb36 tree 0fbef63bfc8b58a623b154a2903d54d51eeccb36 parent 726ae070215767677976fc87d43af2d8cd581162 parent d2815348e8593b286240813ba5ade0052f7139be

Une chaîne d'empreintes

Comme chaque commit scelle son parent, l'identifiant du dernier commit garantit toute l'histoire qui le précède. Deux personnes qui ont le même identifiant de tête ont, octet pour octet, le même passé.

Les anciens commits restent

Après la réécriture, 9327b88 existe toujours, seulement plus aucune branche ne le désigne. Le journal des références le retrouve (cours 107) ; le nettoyage automatique ne l'efface qu'après plusieurs semaines.

Piège courant Réécrire des commits déjà poussés et partagés. Ceux qui les ont récupérés gardent les anciens : leurs branches et les tiennes ne se reconnaissent plus. On ne réécrit que ce qui n'a pas quitté son poste.

Glossaire

Blob
L'objet Git qui contient les octets d'un fichier.
Arbre (tree)
L'objet Git qui liste les noms d'un dossier et ce qu'ils désignent.
Adressage par le contenu
Nommer une donnée par l'empreinte de son contenu.
Paquet (pack)
Un fichier qui regroupe des objets compressés, en partie sous forme de deltas.
Delta
Une version rangée comme la différence avec une autre.
