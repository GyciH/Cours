Le concept

Branches et références

Les objets de Git ne portent pas de noms lisibles. Pour s'y retrouver, Git garde des références : de petits fichiers qui associent un nom à un identifiant. Une branche est une référence qui avance à chaque commit, une étiquette une référence qui ne bouge plus, et HEAD dit où l'on se trouve.

45 min de lecture et de QCM Prérequis · 06 et 103 Exemples · les dépôts SnapSet et Magpie (copies), un dépôt d'essai

L'idée en une phrase

Une branche est un nom posé sur un commit ; committer déplace ce nom vers le nouveau commit ; HEAD dit quel nom déplacer.

L'analogie

Des marque-pages dans un livre qu'on écrit. Le marque-page « en cours » avance à chaque page écrite ; celui de « l'édition de septembre » reste où il est, pour toujours.

À la fin, tu sais

  1. dire ce qu'est une branche, matériellement ;
  2. lire HEAD et les branches distantes ;
  3. comparer deux branches ;
  4. marquer une version par une étiquette.
À retenir origin/principal n'est pas la branche de GitHub : c'est la mémoire locale de ce que GitHub montrait au dernier git fetch. Elle ne bouge que quand on la rafraîchit.

Schéma 1 · Ce qu'est une branche

Quarante et un octets

Dans .git/refs/heads, chaque branche est un fichier qui contient l'identifiant d'un commit. .git/HEAD contient d'ordinaire le nom d'une branche. Faire un commit écrit les objets, puis remplace l'identifiant dans le fichier de la branche que HEAD désigne.

Exemple autonome · Git, lire les références sans ouvrir les fichiersgit symbolic-ref HEAD # refs/heads/etapes-pilote-ui git rev-parse principal # 0d72ba615058e406aa7e8d53d1e464ff973f1b10 git for-each-ref --format="%(refname) %(objectname:short)"

Les branches distantes

refs/remotes/origin/… range ce que git fetch a vu sur GitHub. On ne committe jamais dessus ; git pull commence par les rafraîchir, puis fusionne la branche distante dans la branche locale.

Le suivi

Une branche locale peut suivre une branche distante : git status annonce alors « en avance de 2 commits ». Ce compte compare deux références locales ; sans fetch récent, il peut être faux.

Piège courant Croire qu'une branche « contient » ses commits. Supprimer une branche n'efface aucun commit ; ceux que plus aucun nom ne désigne deviennent seulement invisibles, puis sont nettoyés des semaines plus tard.

Schéma 2 · Comparer, se détacher

En avance, en retard, détaché

Deux branches partagent un ancêtre commun, leur base de fusion. Ce que chacune a depuis se compte en commits : en avance d'un côté, en retard de l'autre. Et HEAD peut désigner directement un commit au lieu d'une branche : c'est l'état détaché.

Exemple autonome · Git, garder un travail fait en HEAD détachégit switch -c essai 2d96b9b # un nom pour le commit abandonné # ou, avant de partir : git switch -c essai

Les fusions restent sur principal

Chaque pull request fusionnée a créé sur principal un commit de fusion que la branche de travail ne reprend pas. C'est normal : ces commits n'apportent aucun fichier nouveau. Le compte « 2, 0 » dit que rien ne manque à principal.

Quand on se détache

En revenant à un ancien commit pour l'examiner, en suivant un git checkout sur un identifiant ou une étiquette, ou pendant un rebase. Regarder est sans risque ; committer l'est aussi, à condition de nommer le résultat avant de partir.

Piège courant Ignorer l'avertissement « you are leaving 1 commit behind ». Le commit existe encore, mais aucun nom ne le désigne : il faut son identifiant, ou le journal des références (cours 107), pour le retrouver.

Schéma 3 · Les étiquettes

Marquer une version

Une étiquette (tag) nomme un commit une fois pour toutes. L'étiquette légère n'est qu'une référence. L'étiquette annotée est un quatrième objet Git, avec auteur, date et message ; c'est elle qu'on emploie pour une version publiée. GitHub construit ses « releases » sur des étiquettes.

Exemple autonome · Git, publier une versiongit tag -a v0.1.6 -m "Magpie 0.1.6" git push origin v0.1.6 # les étiquettes ne partent pas avec un simple push

Pousser une étiquette

git push envoie la branche, pas les étiquettes. On pousse une étiquette par son nom, ou toutes avec --tags. À l'inverse, un clone superficiel ou un fetch partiel peut ne pas les ramener.

Une étiquette ne se déplace pas

Git refuse de recréer une étiquette existante sans -f, et ceux qui l'ont déjà gardent l'ancienne. Une version publiée se corrige par une nouvelle étiquette, jamais en déplaçant l'ancienne.

Piège courant Conclure d'un git tag vide qu'un projet n'a pas de versions. La copie locale de Magpie n'en montre aucune, GitHub en a deux : il manquait seulement le fetch des étiquettes.

Un .gha construit aujourd'hui annonce la même version que celui de la release. Si un apprenant signale un défaut « en 0.1.5 », impossible de savoir lequel. Passer à 0.1.6-dev après chaque étiquette, ou inscrire l'identifiant du commit dans la version (cours 73), lèverait le doute. Relevé par git log et l'API GitHub.

Glossaire

Référence
Un nom qui désigne un identifiant d'objet Git.
HEAD
La référence qui dit où l'on se trouve, d'ordinaire une branche.
HEAD détaché
HEAD qui désigne un commit directement, sans branche.
Branche distante
La copie locale d'une branche du dépôt distant, rafraîchie par fetch.
Étiquette (tag)
Une référence fixe, souvent un objet annoté, qui marque une version.
