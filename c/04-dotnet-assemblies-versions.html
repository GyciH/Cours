Le concept

.NET : runtime,
assemblies et versions

Ton code C# ne tourne jamais seul. Il est compilé dans un fichier, l'assembly, qu'un moteur, le runtime, charge et exécute. Dans notre cas, ce moteur vit à l'intérieur de Rhino : c'est lui qui décide quelle version de .NET ton plugin doit viser.

50 min de lecture et de QCM Prérequis · 01 à 03 Exemples · Cuttlefish, SnapSet, Magpie (le chargeur)

L'idée en une phrase

Un plugin est une assembly (un .dll renommé .gha) compilée pour un runtime précis ; Rhino fournit ce runtime et y charge chaque plugin, une fois, pour toute la session.

L'analogie

Une partition et un orchestre. La partition (l'assembly) est écrite pour une formation donnée (la cible). Rhino 7 a un orchestre classique, .NET Framework ; Rhino 8 un orchestre moderne, .NET 7 et suivants, qui sait encore jouer une partie de l'ancien répertoire.

À la fin, tu sais

  1. distinguer .NET Framework 4.8 et .NET moderne, et dire lequel vise chacun de tes projets ;
  2. dire ce que contient une assembly : nom, version, métadonnées, IL, ressources ;
  3. expliquer pourquoi une bibliothèque chargée ne se remplace pas sans redémarrer Rhino.
À retenir Le langage (C# 7.3, C# 11) et le runtime (.NET Framework 4.8, .NET 7) sont deux choses distinctes. Le cours 01 parlait du premier ; celui-ci parle du second. La cible choisit le runtime, et par défaut, la version du langage.

Schéma 1 · Deux familles de runtime

Pourquoi Cuttlefish et SnapSet ne visent pas la même cible

En 2016, Microsoft a repris .NET de zéro sous le nom .NET Core, devenu simplement « .NET » à partir de la version 5. L'ancien .NET Framework s'arrête à 4.8 : maintenu, mais il n'évolue plus. Rhino a suivi avec un temps de retard.

Piège courant Croire qu'une cible plus récente « marche partout ». Un .gha compilé pour net7.0-windows ne se charge pas dans Rhino 7, ni dans un Rhino 8 qu'on a repassé en .NET Framework. À l'inverse, Cuttlefish en net48 se charge dans les deux : viser l'ancien, c'est élargir le public.

Schéma 2 · Ouvrir une assembly

Un .gha est un .dll qui a changé de nom

Le projet demande <TargetExt>.gha</TargetExt> : c'est tout ce qui distingue un plugin Grasshopper d'une bibliothèque .NET ordinaire. Voici ce qu'on trouve dedans.

La version d'assembly Quatre nombres, 0.1.5.0. Elle sert à .NET pour choisir entre deux copies, et à toi pour savoir ce qui tourne. Magpie l'affiche dans « À propos » ; c'est elle que le chargeur compare page 5.
Piège courant Copier Grasshopper.dll dans le dossier du plugin. Rhino a déjà la sienne en mémoire ; une seconde copie crée deux types GH_Component distincts, et plus rien ne se reconnaît.

Schéma 3 · Le chargement dans Rhino

Chargée une fois, gardée jusqu'à la fermeture

Au démarrage de Grasshopper, chaque .gha des dossiers de bibliothèques passe par les mêmes étapes. Quand une dépendance manque, .NET pose une question, et un plugin peut y répondre.

Piège courant : deux versions d'une même dépendance Deux plugins embarquent chacun leur Newtonsoft.Json, en versions différentes. Le premier chargé gagne pour toute la session ; le second tourne avec une version qu'il n'a pas choisie. C'est le problème que le chargeur de Magpie règle pour son propre Core, en prenant toujours la plus récente.
