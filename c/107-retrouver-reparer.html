Le concept

Retrouver et réparer

Git perd très peu de chose. Un commit qu'on croit effacé reste dans le dépôt des semaines, et un journal local note chaque déplacement de HEAD. Ce cours trie les commandes de réparation selon ce qu'elles touchent : un fichier, l'index, la branche, ou l'histoire partagée.

45 min de lecture et de QCM Prérequis · 103 à 106 Exemples · Magpie, un dépôt d'essai

L'idée en une phrase

Avant de réparer, se demander deux choses : quelle zone est fausse (disque, index, branche), et l'erreur a-t-elle déjà été partagée.

L'analogie

Un classeur de plans. On peut gommer un brouillon sur la table (restore), retirer une feuille de la pile à classer (restore --staged), arracher les dernières pages du classeur (reset), ou, si des copies circulent déjà, ajouter une page « annule la page 12 » (revert).

À la fin, tu sais

  1. choisir entre restore, reset et revert ;
  2. prévoir l'effet de --soft, --mixed, --hard ;
  3. retrouver un commit par le reflog ;
  4. savoir ce qui est vraiment perdu.
À retenir Ce qui a été commité se retrouve presque toujours. Ce qui n'a jamais été ajouté par git add ne se retrouve jamais : avant une commande destructrice, un commit provisoire ou git stash coûte une seconde.

Schéma 1 · Reculer une branche

reset, en trois profondeurs

git reset X déplace la branche courante sur le commit X. Le mode décide jusqu'où descend le recul : la branche seule, la branche et l'index, ou les trois zones. Les commits quittés ne sont pas détruits ; ils ne sont plus pointés par aucune branche.

Exemple autonome · Git, les usages courantsgit reset --soft HEAD~3 # refaire les trois derniers commits en un seul git reset HEAD~1 # défaire le dernier commit, garder les fichiers git reset --hard origin/main # jeter tout le local, repartir du distant git restore --staged f.cs # retirer f.cs du prochain commit

restore, pour un fichier

git restore f recopie l'index sur le disque (mesuré : la modification Marge = 55 a disparu). --staged recopie HEAD dans l'index, le disque garde la modification (mesuré : M M.cs, Marge = 56).

L'ancien nom

Avant Git 2.23, tout passait par git checkout et git reset : checkout -- f pour un fichier, reset HEAD f pour l'index. Ils marchent encore ; restore et switch séparent les deux métiers.

Piège courant Utiliser reset --hard pour « annuler mes modifications » alors qu'on voulait garder un fichier. Il remet tout le disque, sans demander. git restore f limite le dégât au fichier nommé.

Schéma 2 · Le journal

Retrouver ce qu'on croit perdu

Le reflog est un journal local : à chaque fois que HEAD ou une branche bouge (commit, reset, rebase, switch), Git note l'ancienne et la nouvelle position. Un commit sorti d'une branche reste donc accessible par son rang dans ce journal.

Exemple autonome · Git, récupérergit reflog # trouver la ligne d'avant l'erreur git branch sauvetage HEAD@{3} # poser une branche dessus, sans rien écraser git reflog show f # le journal d'une branche précise git fsck --lost-found # les blobs ajoutés puis abandonnés

Local, et à durée limitée

Le reflog ne se pousse pas et ne se clone pas (mesuré : un clone neuf de SnapSet en a 3 lignes). Selon la documentation, Git efface par défaut les entrées après 90 jours, 30 pour les commits plus atteignables.

Poser une branche d'abord

Plutôt que reset --hard sur une entrée du journal, git branch sauvetage <id> : le commit retrouvé est protégé, et on peut comparer avant de choisir.

Piège courant Compter les rangs du reflog avant d'avoir relu la liste. Chaque reset, y compris un essai raté, ajoute une ligne en tête et décale tous les numéros : HEAD@{2} n'est plus ce qu'il était une commande plus tôt.

Schéma 3 · Défaire en public

revert : un commit qui en annule un autre

Une fois un commit poussé, d'autres l'ont peut-être déjà. Le retirer par reset réécrit l'histoire sous leurs pieds (cours 105). git revert calcule l'inverse du commit et l'enregistre comme un nouveau commit : l'histoire s'allonge, elle n'est jamais réécrite.

Exemple autonome · Git, annuler en publicgit revert 2a60745 # un commit inverse, message prérempli git revert -m 1 75372b2 # une fusion : garder le côté du parent 1 git revert --no-commit A B # plusieurs, en un seul commit git revert --abort # en cas de conflit, tout annuler

Plus le commit est vieux…

…plus son inverse a de chances de buter sur ce qui a suivi. Mesuré : annuler c1, qui créait M.cs, donne un conflit, puisque c2 à c4 ont changé ce fichier ensuite. Le conflit se résout comme au cours 106.

Revert ou correction ?

Un revert retire tout le commit. S'il apportait aussi du bon, mieux vaut un commit correctif qui ne touche que le défaut : c'est ce qu'a fait Magpie le 7 septembre (page 5).

Piège courant Annuler une fusion par revert, puis refusionner la même branche plus tard. Git voit ses commits comme déjà intégrés et ne les rejoue pas : il faut d'abord annuler le revert lui-même (git revert du commit « Revert … »).

Une réparation en avant, dans Magpie

À surveiller · master peut cesser de compiler sans que rien ne le signale 6fbb234 et ac278b5 sont deux commits directs sur master, sans pull request (un seul parent chacun) ; Magpie n'a pas de dossier .github/workflows. Pendant 3 h 44, un collaborateur qui tirait master récupérait un plugin qui ne compilait pas. Le correctif est exemplaire (il nomme le commit fautif), mais la détection reposait sur la vigilance. Déduit : une compilation automatique à chaque push, ou au moins avant de pousser, aurait arrêté 6fbb234. Relevé sans rien modifier.

Glossaire

Reflog
Le journal local des positions successives de HEAD et des branches.
Reset
Le déplacement d'une branche, avec ou sans l'index et le disque.
Revert
Un commit qui applique l'inverse d'un autre.
Blob orphelin
Un contenu stocké que plus rien ne désigne (« dangling »).
Réparer en avant
Corriger par un nouveau commit plutôt que d'effacer.
