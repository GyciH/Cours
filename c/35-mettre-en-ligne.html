Le concept

Mettre en ligne

Sur ton poste, Magpie Web tourne avec deux serveurs, Vite et le backend. En ligne, il n'en reste qu'un : une application Node hébergée chez o2switch, qui sert à la fois la page construite et l'API. Mettre en ligne, c'est envoyer le code, le construire sur place et redémarrer, sans jamais toucher aux données ni aux secrets du serveur.

50 min de lecture et de QCM Prérequis · 06, 30, 31 et 34 Exemples · outils/deployer.sh, app.cjs, README.md (Magpie web)

L'idée en une phrase

Le code voyage, l'état reste : le dépôt part sur le serveur à chaque mise en ligne, mais la base et le fichier .env du serveur ne sont jamais envoyés ni écrasés.

L'analogie

Changer le moteur d'une voiture sans vider le coffre ni changer les clés. Le moteur, c'est le code ; le coffre, la base ; les clés, les mots de passe du serveur.

À la fin, tu sais

  1. suivre deployer.sh, du poste au redémarrage ;
  2. dire ce qui part en ligne et ce qui reste sur place ;
  3. régler une variable d'environnement sans l'écrire dans le code ;
  4. dire pourquoi l'administration exige HTTPS.
À retenir Compute ne part pas en ligne : il reste sur ton poste, faute de licence serveur. L'hébergement prévoit de le joindre par un tunnel protégé par une clé partagée (COMPUTE_API_KEY) ; ce test complet est encore à faire (journal web, § 21).

Schéma 1 · Le trajet d'une mise en ligne

Une commande, six étapes

deployer.sh se lance depuis ton poste. Il n'a pas besoin que le serveur accède à GitHub : il lui envoie lui-même le code, par SSH, puis lui fait construire et redémarrer l'application.

outils/deployer.sh · 16–21REF="${1:-HEAD}" ROOT="$(git rev-parse --show-toplevel)" COMMIT="$(git -C "$ROOT" rev-parse --short "$REF")" echo "Envoi de web/ @ $COMMIT vers o2switch:~/magpie-app" git -C "$ROOT" archive --format=tar "$REF:web" | ssh o2switch 'tar -x -C ~/magpie-app'

Le commit, pas la copie de travail

git archive emballe le dossier web/ tel qu'il est dans un commit. Un fichier modifié mais pas commité ne part pas. La sortie de git archive entre directement dans tar sur le serveur, par le tube | : aucun fichier intermédiaire.

Construire sur place

Le serveur installe les paquets, puis lance npm run build pour produire dist/. Passenger tourne en NODE_ENV=production, qui saute les paquets de développement ; Vite en est un, d'où --include=dev (ligne 27).

Piège courant Corriger un fichier, lancer deployer.sh, et retrouver l'ancienne version en ligne : la correction n'était pas commitée. Le script écrit le commit envoyé dans un fichier DEPLOYED sur le serveur (ligne 29) ; c'est la première chose à lire en cas de doute.

Schéma 2 · Le code et l'état

Ce qui part, ce qui reste

Tout ce qui est propre à une installation (la base, les secrets, les paquets installés, le front construit) est exclu du dépôt par .gitignore. Comme git archive n'emballe que le dépôt, la mise en ligne ne peut pas l'écraser.

.gitignore (racine du dépôt) · 371–382, extraitsweb/magpie.db web/dist/ .env .env.* !.env.example

La base se reconstruit

magpie.db n'est pas versionnée, mais data/ l'est : le catalogue, les exercices, les parcours et la liste des composants autorisés. data/README.md donne l'ordre pour tout reconstruire : migrate-catalog, les imports, puis restore-authorized.

Les réglages hors du code

app.cjs lit le .env posé à côté de lui (lignes 10–11). Les variables réglées dans cPanel gardent la priorité. .env.example, lui, est versionné : il liste les noms à remplir, jamais les valeurs.

Piège courant Restaurer les composants autorisés avec authorize-components.mjs. Il travaille par nom, et 18 noms sont partagés par plusieurs composants : « Addition » active celle des nombres et celle des vecteurs. restore-authorized.mjs travaille par typeGuid, sans ambiguïté (data/README.md).

Schéma 3 · En ligne, tout le monde peut frapper

Les réglages qui protègent

Sur ton poste, seul toi atteins le serveur. En ligne, n'importe qui peut lui envoyer une requête. Les gardes du cours 33 restent les mêmes ; ce sont les réglages qui changent.

.env.example · 1–9# Copier en .env (ignoré par git) et remplir. … MAGPIE_ADMIN_USER=enseignant MAGPIE_ADMIN_PASSWORD= # MAGPIE_ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173 # COMPUTE_TARGET=http://localhost:6500 # COMPUTE_TIMEOUT_MS=20000 # Clé partagée avec Rhino Compute (lancé avec RHINO_COMPUTE_KEY), obligatoire derrière un tunnel # COMPUTE_API_KEY=

Fermé par défaut

Sans MAGPIE_ADMIN_PASSWORD, l'administration répond 503 : elle est fermée, pas ouverte à tous. De même, le catalogue démarre sans aucun composant autorisé ; l'enseignant les active un par un.

Une seule origine

En ligne, la page et l'API viennent du même serveur : le navigateur n'a aucun appel « d'ailleurs » à autoriser, et MAGPIE_ALLOWED_ORIGINS n'a pas à être réglée. Elle ne sert qu'en développement, quand Vite et le backend ont chacun leur port.

Piège courant Ouvrir l'administration sans HTTPS. HTTP Basic envoie l'identifiant et le mot de passe en base64 à chaque requête : c'est un codage, pas un chiffrement, et n'importe qui sur le chemin le relit. Le README exige AutoSSL et la redirection de HTTP vers HTTPS.

Glossaire

Passenger
Le serveur d'applications d'o2switch : il lance app.cjs et lui donne un port.
SSH
Une connexion chiffrée pour lancer des commandes sur une autre machine.
Tunnel
Un passage chiffré qui rend joignable un service resté sur ton poste.
AutoSSL
Le certificat HTTPS gratuit et renouvelé tout seul par cPanel.
Seed
Les données versionnées qui suffisent à reconstruire une base vide.
