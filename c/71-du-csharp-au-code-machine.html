Le concept

Du C# au code machine

Le processeur ne comprend pas le C#. Entre le texte que tu écris et les instructions qu'il exécute, il y a deux traductions : le compilateur (Roslyn) transforme le C# en IL, un langage intermédiaire rangé dans le .gha ; puis, dans Rhino, le JIT transforme cet IL en code machine, méthode par méthode, au moment où elle sert pour la première fois.

50 min de lecture et de QCM Prérequis · 04 et 05 Exemples · ChargeurCore, Directory.Build.props (Magpie), csproj (SnapSet)

L'idée en une phrase

Le .gha transporte un code portable et décrit (l'IL et ses métadonnées) ; le code machine n'existe qu'en mémoire, fabriqué sur place par le JIT, pour le processeur qui l'exécute.

L'analogie

Une partition : le compositeur l'écrit une fois (compilation), chaque orchestre la joue avec ses instruments (JIT). La partition ne dépend pas de la salle ; le son, si.

À la fin, tu sais

  1. situer compilation, chargement et JIT ;
  2. lire quelques lignes d'IL ;
  3. distinguer version du langage et du runtime ;
  4. dater une erreur : compilation ou exécution.
À retenir Une assembly (.dll, .gha) est un fichier PE, comme un .exe, qui contient des métadonnées (types, méthodes, version, références) et de l'IL. Les métadonnées se lisent sans rien exécuter : c'est ce qui permet à Grasshopper de lister les composants d'un .gha, et à Magpie de connaître la version d'un Core embarqué.

Schéma 1 · Une fonction, trois formes

Ce que contient vraiment un .gha

L'IL (Intermediate Language) est le langage commun à C#, F# et VB : tous se compilent vers lui. Il décrit les opérations sur une pile, sans registres ni adresses, ce qui le rend indépendant du processeur. Il reste lisible, et un décompilateur peut en retrouver un C# très proche de l'original.

Exemple autonome · outilsildasm SnapSet.Conception.gha # SDK .NET Framework : l'IL, méthode par méthode ilspycmd SnapSet.Conception.gha # ILSpy : retrouve un C# lisible sharplab.io # en ligne : C#, IL et x64 côte à côte node --print-bytecode --print-bytecode-filter=somme somme.js

Pas de secret dans un .gha

Puisque l'IL se décompile, une clé, un mot de passe ou une logique de correction écrits dans le plugin sont lisibles par qui le veut. C'est la raison pour laquelle Magpie corrige côté serveur (cours 33) et garde ses secrets dans l'environnement (cours 63).

Debug et Release

En Debug, le compilateur garde chaque variable et ajoute des instructions vides pour que le débogueur s'arrête où tu veux. En Release, il simplifie, et le JIT optimise davantage : on ne mesure les performances qu'en Release.

Piège courant Croire qu'« obfusquer » ou compiler en Release protège le code. Cela le rend pénible à lire, pas secret. Ce qui doit rester secret ne quitte pas le serveur.

Schéma 2 · Le JIT

Compiler au dernier moment

Le JIT (just in time) compile une méthode la première fois qu'elle est appelée, puis garde le résultat. Il connaît la machine réelle : il peut utiliser les instructions de ce processeur précis, et observer quelles méthodes servent souvent pour les recompiler mieux. JavaScript suit la même logique, avec un interprète devant.

Exemple autonome · mesuré pour ce coursfunction f(n) { let s = 0; for (let i = 0; i < n; i++) s += i * i % 7; return s; } f(1e7); node jit.js # ≈ 100 ms node --jitless jit.js # ≈ 500 ms

Le premier appel coûte

Le temps de compilation est payé au premier appel : c'est une part du délai au chargement d'un plugin, ou au premier clic sur un composant. Les appels suivants sont rapides.

Et sans JIT ?

On peut aussi compiler à l'avance (AOT) : démarrage immédiat, mais un fichier par processeur, et pas de chargement dynamique. Un plugin chargé par Rhino reste donc en IL, compilé par le JIT de Rhino.

Piège courant Mesurer une seule exécution. La première inclut la compilation, et en .NET le code ne passe au niveau optimisé qu'après une trentaine d'appels. On mesure plusieurs fois, en Release, et on écarte le premier passage.

Schéma 3 · Le moment de chaque erreur

Compilé ne veut pas dire chargeable

Le compilateur vérifie le texte, contre les bibliothèques présentes sur ton poste. Chez l'utilisateur, d'autres choses peuvent manquer : une bibliothèque, une version. Ces erreurs-là n'apparaissent qu'au chargement, ou même seulement quand le JIT compile la méthode qui en a besoin.

Exemple autonome · csproj<TargetFramework>net7.0-windows</TargetFramework> <!-- les API disponibles --> <LangVersion>latest</LangVersion> <!-- les mots du langage --> <Optimize>true</Optimize> <!-- Release --> <TreatWarningsAsErrors>true</TreatWarningsAsErrors>

Deux versions différentes

La version du langage (C# 11, 12…) décide des mots que le compilateur accepte. La version du runtime (.NET 7, .NET Framework 4.8) décide des classes disponibles à l'exécution : c'est elle qu'impose Rhino.

Les analyseurs

Roslyn accepte des extensions qui inspectent le code pendant la compilation et émettent des avertissements (les codes CA, RS…). Elles tournent dans le compilateur : on leur interdit d'écrire des fichiers.

Piège courant Un composant qui « disparaît » de Grasshopper sans message. Souvent, son constructeur utilise un type d'une bibliothèque introuvable : le JIT ne peut pas le compiler, et Grasshopper l'écarte. Le débogueur attaché à Rhino (cours 47), avec arrêt sur toutes les exceptions, montre laquelle.

Glossaire

IL
Le langage intermédiaire de .NET, indépendant du processeur, rangé dans les assemblies.
JIT
Le compilateur qui traduit l'IL en code machine au premier appel de chaque méthode.
AOT
La compilation en code machine à l'avance, avant la distribution.
Métadonnées
La description des types, méthodes et références d'une assembly.
Analyseur
Une extension du compilateur qui inspecte le code et émet des avertissements.
