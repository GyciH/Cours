Le concept

Origines : CORS et CSRF

Un navigateur ouvre en même temps des onglets de ta banque, de ton webmail et de n'importe quel site. Pour qu'une page ne lise pas les données d'une autre, il applique la règle de même origine. CORS permet à un serveur d'ouvrir une exception ; CSRF est l'attaque qui passe à côté.

50 min de lecture et de QCM Prérequis · 61 Exemples · compute-proxy.mjs, vite.config.js (Magpie web)

L'idée en une phrase

Le script d'une page peut envoyer des requêtes partout, mais ne peut lire la réponse d'une autre origine que si ce serveur l'y autorise par un en-tête Access-Control-Allow-Origin.

L'analogie

Une boîte aux lettres d'immeuble. N'importe qui peut glisser une lettre dans n'importe quelle boîte (envoyer), mais seul le résident ouvre la sienne (lire). CORS, c'est le résident qui confie un double de sa clé à un voisin nommé.

À la fin, tu sais

  1. dire si deux adresses ont la même origine ;
  2. lire une erreur CORS et la corriger ;
  3. prévoir quand le navigateur envoie OPTIONS ;
  4. expliquer une attaque CSRF et ses parades.
À retenir CORS est une protection du navigateur, pas du serveur. Un script Node, curl ou Postman l'ignorent complètement. Il ne remplace donc jamais l'authentification : il empêche seulement une page étrangère de lire ce que ton navigateur reçoit.

Schéma 1 · La règle de même origine

Envoyer, oui ; lire, sur autorisation

Quand la page de A appelle B, le navigateur ajoute l'en-tête Origin: A. B répond comme il veut ; le navigateur regarde alors si la réponse autorise A. Sinon, la console affiche une erreur CORS et le script ne voit rien.

Exemple autonome · Nodeconst AUTORISEES = new Set(["https://magpie.example"]); function cors(req, res) { res.setHeader("Vary", "Origin"); // la réponse dépend de l'origine const o = req.headers.origin; if (AUTORISEES.has(o)) res.setHeader("Access-Control-Allow-Origin", o); }

Pourquoi Vary: Origin

Si la réponse change selon l'origine, un cache intermédiaire doit le savoir. Sans Vary, il pourrait resservir à B la réponse préparée pour A, avec le mauvais en-tête.

La solution la plus simple

Une seule origine pour tout. En production, le serveur Magpie sert lui-même le front ; en développement, Vite relaie /api vers le backend. Le navigateur ne voit jamais deux origines.

Piège courant Répondre Access-Control-Allow-Origin: * pour « faire marcher ». N'importe quel site peut alors lire l'API depuis le navigateur de tes visiteurs. Une liste explicite d'origines, comme ALLOWED_ORIGINS, ne coûte que quelques lignes.

Schéma 2 · La requête préalable

Demander avant d'envoyer

Pour une requête qu'un simple formulaire HTML ne pourrait pas produire (méthode PUT ou DELETE, en-tête personnalisé, corps en application/json), le navigateur envoie d'abord un OPTIONS. Si la réponse ne l'autorise pas, la vraie requête ne part jamais.

Exemple autonome · requête simple ou pasfetch(url) // GET : simple, pas d'OPTIONS fetch(url, { method: "POST", body: formData }) // formulaire : simple fetch(url, { method: "POST", body: JSON.stringify(x), headers: { "Content-Type": "application/json" } }) // JSON : OPTIONS d'abord fetch(url, { method: "DELETE" }) // DELETE : OPTIONS d'abord

Les trois types « simples »

application/x-www-form-urlencoded, multipart/form-data et text/plain : ceux qu'un formulaire HTML sait envoyer. Tout autre Content-Type déclenche la question préalable.

Répondre à OPTIONS

Le serveur répond vite, sans corps et sans traitement : 204, plus les en-têtes Allow-Methods et Allow-Headers. Magpie le fait avant même la garde d'administration.

Piège courant Exiger l'authentification sur OPTIONS. Le navigateur n'y joint jamais d'identifiants : la question préalable reçoit 401, la vraie requête n'est jamais envoyée, et l'erreur affichée parle de CORS au lieu de parler d'authentification.

Schéma 3 · La falsification de requête

CSRF : agir au nom d'un autre

Le navigateur joint d'office aux requêtes vers un site ce qu'il garde pour lui : cookies, identifiants HTTP Basic déjà saisis. Une page piégée qui soumet un formulaire vers ce site agit donc avec les droits de la victime, sans jamais lire la réponse.

Exemple autonome · une garde d'originefunction origineAcceptee(req) { const o = req.headers.origin; // posé par le navigateur, pas modifiable par la page return !o || o === "https://magpie.example"; // absent : outil en ligne de commande, non navigateur } if (req.method === "POST" && !origineAcceptee(req)) { res.writeHead(403); return res.end(); }

Pourquoi CORS ne suffit pas

CORS règle la lecture par un script. Un formulaire n'a rien à lire : il lui suffit d'être reçu. L'action « basculer un composant » est faite, même si la page piégée ne voit pas la réponse.

Les cookies SameSite

Un cookie marqué SameSite=Lax ou Strict n'est pas joint aux requêtes POST venues d'un autre site. Les identifiants HTTP Basic n'ont pas cette option : la parade passe par Origin ou le type du corps.

Piège courant Croire qu'une route POST qui attend du JSON est à l'abri parce qu'un formulaire « n'envoie pas de JSON ». Un formulaire en text/plain peut produire un corps qui se lit comme du JSON valide. Seule la vérification du Content-Type ferme cette porte.

Glossaire

Origine
Le triplet schéma, hôte, port d'une adresse web.
CORS
Les en-têtes par lesquels un serveur autorise une autre origine à lire ses réponses.
Requête préalable
L'OPTIONS que le navigateur envoie avant une requête non simple.
CSRF
Faire envoyer par le navigateur d'une victime une requête qu'elle n'a pas voulue.
SameSite
L'attribut de cookie qui l'empêche de partir avec les requêtes d'un autre site.
