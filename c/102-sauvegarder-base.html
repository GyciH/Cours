Le concept

Sauvegarder une base

Une base SQLite tient dans un fichier, et l'on est tenté de la sauvegarder comme n'importe quel fichier : une copie. Tant qu'une connexion peut écrire, cette copie risque d'être fausse, sans que rien ne le signale. SQLite sait faire une copie juste d'une base ouverte ; encore faut-il la faire, la garder, et savoir la restaurer.

45 min de lecture et de QCM Prérequis · 100 et 101 Exemples · data/README.md, deployer.sh, compute-proxy.mjs (Magpie)

L'idée en une phrase

Ce qui ne peut pas se reconstruire doit se copier, par l'outil de la base, régulièrement, ailleurs, et une copie n'est sûre qu'une fois restaurée avec succès.

L'analogie

Photographier un tableau blanc pendant que quelqu'un efface une ligne pour la réécrire : la photo montre un tableau qui n'a jamais existé. Il faut demander une pause, ou photographier la version propre.

À la fin, tu sais

  1. distinguer ce qui se reconstruit de ce qui se sauvegarde ;
  2. dire pourquoi une simple copie peut mentir ;
  3. copier une base ouverte sans risque ;
  4. organiser des sauvegardes utiles.
À retenir Magpie a déjà la moitié de la réponse : sa base se reconstruit depuis des fichiers versionnés, et la procédure a été vérifiée (data/README.md). Ce cours regarde l'autre moitié, ce qui s'accumule ensuite sur le serveur.

Schéma 1 · Copier le fichier

Une copie qui ment

En mode delete, une grosse transaction écrit déjà dans le fichier avant de valider. En mode WAL, les validations récentes vivent dans -wal jusqu'à leur recopie. Dans les deux cas, le fichier principal seul, copié au mauvais moment, ne contient pas un état validé de la base.

magpie/web/outils/deployer.sh · ligne 13# magpie.db n'est pas versionnée : elle n'est ni envoyée ni écrasée ici.

Le déploiement n'y touche pas

Le script de mise en ligne envoie le code et laisse la base du serveur en place : une mise à jour ne perd aucun réglage. Mais cela veut aussi dire qu'aucune copie de cette base n'existe ailleurs que sur le serveur.

Pourquoi l'intégrité ne suffit pas

integrity_check vérifie que les pages et les index se tiennent. Une copie qui a saisi une transaction à moitié peut être parfaitement bien formée : elle contient seulement des lignes qui n'auraient pas dû y être, ou pas encore.

Piège courant Télécharger magpie.db par SFTP pendant que l'application tourne, et croire avoir une sauvegarde. Elle sera juste la plupart du temps, ce qui rend l'exception d'autant plus difficile à soupçonner.

Schéma 2 · La copie sûre

Demander la copie à SQLite

SQLite sait lire un état validé pendant que d'autres écrivent : c'est ce que fait n'importe quelle requête. Ses outils de copie s'appuient là-dessus. Ils produisent un fichier autonome, cohérent, qui s'ouvre seul, sans -wal ni journal.

Exemple autonome · Node 22, un script de sauvegarde datéeimport { DatabaseSync, backup } from "node:sqlite"; const db = new DatabaseSync("magpie.db", { timeout: 5000 }); const jour = new Date().toISOString().slice(0, 10); // 2026-10-25 await backup(db, `sauvegardes/magpie-${jour}.db`); db.close();

Pendant que le serveur tourne

backup copie la base par paquets de pages. Si une écriture survient entre deux paquets, il recommence, pour finir sur un état cohérent. Sur une base de 1,1 Mo, le tout dure 15 ms : le serveur ne s'en aperçoit pas.

VACUUM INTO

Une seule instruction SQL, utilisable depuis n'importe quel outil, qui écrit une copie compactée. Elle refuse d'écrire sur un fichier existant : chaque sauvegarde porte donc un nom nouveau, ce qui va bien avec des copies datées.

Piège courant Garder la sauvegarde dans le même dossier que la base, sur le même serveur. Une erreur de manipulation, un dossier effacé ou un hébergement perdu emportent l'original et sa copie ensemble.

Schéma 3 · Une sauvegarde qui sert

Régulière, gardée, ailleurs, essayée

On ne choisit pas une sauvegarde pour le jour où tout va bien, mais pour celui où l'on s'aperçoit, trois jours plus tard, qu'un import a abîmé les données. Il faut alors une copie d'avant, intacte, accessible, et une procédure déjà essayée pour la remettre en place.

magpie/web/data/README.md · lignes 48 à 50La procédure complète ci-dessus a été vérifiée : base supprimée puis reconstruite, résultat comparé à l'originale — 725 composants, 8 autorisés, 5 exercices, 1 parcours, et les 5 configurations de validation identiques.

Une restauration essayée

Ces trois lignes sont exactement ce qu'on attend d'une sauvegarde : on a reconstruit, puis comparé à l'original. Le même geste vaut pour une copie : l'ouvrir ailleurs, lancer integrity_check, compter les lignes de chaque table.

Restaurer, c'est remplacer

On arrête l'application, on remplace magpie.db par la copie, on supprime d'éventuels -wal et -shm restés à côté, puis on redémarre. Un -wal ancien rejoué sur une copie neuve la mélangerait à un autre état.

Piège courant N'avoir qu'une copie, écrasée chaque nuit. Si l'erreur date d'avant-hier, la copie de cette nuit la contient déjà : on a sauvegardé le problème.

Glossaire

Sauvegarde
Une copie cohérente, gardée ailleurs, dont on a vérifié la restauration.
Seed
Les fichiers versionnés à partir desquels une base se reconstruit.
Point de contrôle
La recopie des pages de -wal dans le fichier principal (checkpoint).
Restauration
Le remplacement d'une base par une copie, application arrêtée.
Contrôle d'intégrité
La vérification que les pages et les index d'une base se tiennent.
