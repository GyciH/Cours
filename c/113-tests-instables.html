Le concept

Tests instables

Un test instable (flaky) donne tantôt vert, tantôt rouge, sur le même code. Il ne signale pas un défaut du programme mais une dépendance cachée du test : l'heure, la machine, l'ordre d'exécution. Ce cours reproduit quatre de ces dépendances et mesure leur effet.

45 min de lecture et de QCM Prérequis · 109, 72 dates et fuseaux Exemples · SnapSet, dépôts d'essai

L'idée en une phrase

Un test doit être une fonction : mêmes entrées, même verdict ; tout ce qu'il lit d'autre (l'horloge, le disque, le voisin) doit être fixé par lui.

L'analogie

Un détecteur de fumée qui sonne quand on fait griller du pain. Au bout d'une semaine on retire la pile. Le jour de l'incendie, il ne sonne plus : la fausse alerte a coûté plus cher que l'alerte manquée.

À la fin, tu sais

  1. reconnaître les cinq sources d'instabilité ;
  2. remplacer une attente par une valeur fixée ;
  3. isoler un test de ses voisins ;
  4. attendre correctement l'asynchrone.
À retenir Relancer un test rouge jusqu'à ce qu'il passe n'est pas une correction. Un test qui échoue une fois sur cinquante a un défaut, à traiter comme un défaut du programme : on le reproduit, on trouve la dépendance, on la fixe.

Schéma 1 · Le temps

Un chronomètre dans un test

Vérifier qu'une opération « prend moins de N ms » paraît raisonnable. Mais la durée dépend de tout ce que fait la machine à ce moment : autres processus, compilation à la volée, mémoire. Le test mesure la machine autant que le code.

Exemple autonome · node:test, le test qui chronomètretest("le calcul prend moins de 6 ms", () => { const t0 = performance.now(); travail(); const ms = performance.now() - t0; assert.ok(ms < 6, `${ms.toFixed(2)} ms`); // vert ou rouge selon la machine });

L'attente, même piège

« Attendre 100 ms puis vérifier » échoue quand la machine est lente, et ralentit tout quand elle est rapide. On attend un événement (une promesse, un signal), pas une durée.

L'horloge, une entrée

Un code qui appelle DateTime.Now donne un résultat différent à chaque lancement. On lui passe l'heure en paramètre, ou une horloge (TimeProvider en .NET 8, mock.timers en Node).

Piège courant Augmenter le seuil à chaque fausse alerte. Le test finit par accepter 10 fois la durée normale : il ne détecte plus rien, et il échoue encore les jours de forte charge.

Schéma 2 · Lieu, ordre, asynchrone

Ce que le test lit sans le dire

Le fuseau de la machine, l'état laissé par le test précédent, une promesse qu'on n'attend pas : trois dépendances invisibles dans le code du test, qui ne se manifestent que dans certaines conditions.

Exemple autonome · node:test, les trois correctionsnew Date(…).toLocaleDateString("fr-FR", { timeZone: "Europe/Paris" }) // lieu explicite beforeEach(() => { panier = []; }); // état neuf par test test("…", async () => { assert.equal(await charge(), 42); }); // attendre

Le fuseau de qui ?

Le serveur de Magpie, le poste de Jérémy et un runner de CI n'ont pas forcément le même fuseau. Un test de date qui passe sur l'un peut échouer sur l'autre, seulement entre 22 h et minuit (cours 72).

Lancer un test seul

--test-name-pattern (Node) ou --filter (dotnet test) lancent un test isolé. S'il échoue seul et passe avec les autres, il dépend d'un voisin.

Piège courant Croire que l'ordre des tests est garanti. xUnit lance les classes de test en parallèle, et beaucoup d'outils peuvent mélanger l'ordre exprès ; un test qui a besoin d'un voisin pour passer finira par le perdre.

Schéma 3 · Les parades

Tout ce qui varie devient une entrée

Les tests de SnapSet appliquent les parades une à une : GUID fixé, date posée plutôt qu'attendue, dossier temporaire neuf pour chaque test, culture remise en place quoi qu'il arrive. Une seule dépendance reste, vers la machine elle-même.

Code réel · SnapSet, EcrivainGenerationTests.cs, lignes 88 et 98File.SetLastWriteTimeUtc(chemin, Autrefois); // date posée dans le passé … Assert.Equal(Autrefois, File.GetLastWriteTimeUtc(chemin)); // donc pas réécrit

Pourquoi une date de 2020

Pour vérifier qu'un fichier n'a pas été réécrit, on pourrait attendre une seconde et comparer les dates. Poser une date ancienne rend la preuve instantanée et certaine : une réécriture la remplacerait par aujourd'hui.

try / finally

Si l'assertion échoue, l'exception saute la fin du test. Sans finally, la culture fr-FR resterait en place pour la suite : un échec en provoquerait d'autres, ailleurs.

Piège courant Écrire dans un dossier fixe (« C:\temp\essai »). Deux tests qui tournent en même temps s'écrasent mutuellement, et un reste d'un lancement interrompu fausse le suivant. Un nom unique par test, effacé à la fin.

Glossaire

Test instable (flaky)
Un test au verdict variable sur un code inchangé.
Isolement
L'indépendance d'un test vis-à-vis des autres et de la machine.
État partagé
Une donnée qu'un test modifie et qu'un autre lit.
Horloge injectée
Une source de temps passée au code, que le test fixe.
Fausse alerte
Un échec qui ne correspond à aucun défaut du programme.
