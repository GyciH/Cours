Le concept

Git et GitHub
au quotidien

Git garde l'histoire de ton projet, photo après photo, sur ton poste. GitHub en garde une copie en ligne et ajoute ce qu'il faut pour travailler à plusieurs : pull requests, issues, jalons. Magpie compte 134 commits et 25 pull requests fusionnées.

50 min de lecture et de QCM Prérequis · aucun Exemples · Magpie : historique réel au 22/10/2026

L'idée en une phrase

Un commit est une photo de tout le projet, avec un message qui dit pourquoi ; une branche est une étiquette qui avance de photo en photo ; GitHub héberge une copie et fait fusionner les branches par pull request.

L'analogie

Les indices d'un plan d'architecte. Chaque version porte un indice, une date et la nature de la modification. On peut toujours ressortir l'indice C, et une variante se dessine sur un calque à part avant d'être reportée sur le plan principal.

À la fin, tu sais

  1. dire où se trouve une modification : dossier, préparation, dépôt local, GitHub ;
  2. lire un graphe de branches et reconnaître une fusion ;
  3. suivre la vie d'une pull request, de la branche à la fusion, et relier un commit à une issue.
À retenir Git ne garde que ce que tu lui confies par un commit. Un fichier modifié mais jamais commité n'a pas d'histoire ; un commit jamais poussé n'existe que sur ton poste.

Schéma 1 · Ce qu'est un commit

Une photo, un parent, un message

Chaque commit pointe vers celui qui le précède : l'historique est une chaîne. Son identifiant, un hash, est calculé à partir de son contenu ; deux commits différents ne peuvent pas avoir le même.

Piège courant Un titre comme « modifs » ou « wip ». Dans six mois, git log sera ta seule mémoire du pourquoi. Les commits de Magpie disent ce qui change pour l'utilisateur : « Composant en erreur : rouge, plus d'échec 500 à Tester ».

Schéma 2 · Branches et fusions

Travailler à côté, puis reporter sur master

Une branche est une ligne de commits qui part d'un point de master. Quand le travail est prêt, une fusion crée un commit à deux parents : la suite de master, et le bout de la branche. Voici les deux dernières pull requests de Magpie.

Pourquoi travailler en branche

Master reste toujours dans un état qui compile et qui marche. Une idée abandonnée se jette avec sa branche, sans avoir touché au reste. Et la pull request montre d'un bloc tout ce que la branche change.

Piège courant : le conflit Deux branches modifient les mêmes lignes d'un fichier. Git ne choisit pas : il marque le fichier avec <<<<<<<, =======, >>>>>>> et attend que tu gardes la bonne version. C'est normal, pas une panne.

Schéma 3 · Ce que GitHub ajoute

Pull requests, issues, jalons

Git ne connaît que des commits et des branches. GitHub ajoute une couche d'organisation autour : on discute d'un problème dans une issue, on propose un changement par une pull request, on regroupe le tout par jalon.

Piège courant : pousser un secret Une fois poussé, un fichier reste dans l'historique même si on le supprime ensuite. Le .gitignore de Magpie exclut donc .env (clés et adresses du serveur), launchSettings.json (chemin de Rhino du poste) et pedagogie/propositions/, qui contient les corrigés en clair.

  • 2Le résultat du build webweb/dist/ se régénère par npm run build ; le serveur le produit lui-même.
  • 3Les secrets.env porte la clé d'API de Compute et les adresses : jamais dans Git. Le motif .env.* couvre les variantes.
  • 4L'exceptionLe ! réintègre un fichier : .env.example, sans valeurs, montre quelles variables définir.
  • 5Ce qui dépend du posteMême logique que RHINO_PATH au cours 05 : un modèle est versionné, la copie locale non.
  • 6Ce qui donnerait la réponseSpécifique à Magpie : un corrigé poussé sur le dépôt serait lisible par qui y a accès.
À retenir Le .gitignore n'agit que sur les fichiers pas encore suivis. Un fichier déjà commité reste suivi même si on l'ajoute à la liste ; il faut l'en retirer explicitement avec git rm --cached.

Glossaire

Commit
Photo du projet, avec un parent, un auteur et un message.
Branche
Étiquette mobile posée sur le dernier commit d'une ligne de travail.
Pull request
Demande, sur GitHub, de fusionner une branche dans une autre.
origin
Le nom par défaut du dépôt distant (ici, GitHub).
