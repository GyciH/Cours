Le concept

Résoudre un conflit

Une fusion combine seule les changements qui touchent des endroits différents. Quand deux branches modifient les mêmes lignes, Git ne choisit pas : il s'arrête, écrit les deux versions dans le fichier et te laisse décider. Un conflit n'est pas une erreur, c'est une question posée.

45 min de lecture et de QCM Prérequis · 105 Exemples · SnapSet, Magpie, trois dépôts d'essai

L'idée en une phrase

Un conflit, c'est trois versions d'un même passage (l'ancêtre, la tienne, l'autre) que Git ne sait pas réunir ; le résoudre, c'est écrire la quatrième.

L'analogie

Deux relecteurs corrigent la même phrase d'un rapport, chacun à sa façon. La secrétaire qui reporte les corrections ne tranche pas : elle recopie les deux en marge et demande à l'auteur laquelle garder.

À la fin, tu sais

  1. lire les marqueurs d'un conflit ;
  2. voir la base avec zdiff3 ;
  3. prévenir les conflits de fins de ligne ;
  4. trancher un binaire sans te tromper de côté.
À retenir Tant que le conflit n'est pas résolu, rien n'est perdu : git merge --abort ou git rebase --abort ramène exactement à l'état d'avant. Mesuré : après l'abandon, le dépôt d'essai est revenu sur son commit, sans fichier modifié.

Schéma 1 · Les trois versions

Ce que Git garde pendant le conflit

Pendant le conflit, l'index ne contient plus une version du fichier mais trois, numérotées : la base, la tienne, l'autre. git status marque le fichier UU (modifié des deux côtés, non fusionné). Le fichier de travail, lui, contient le mélange avec marqueurs.

Exemple autonome · Git, voir et résoudregit config --global merge.conflictStyle zdiff3 # montrer la base git status --short # UU M.cs git diff # diff combiné : ++ et + en deux colonnes # corriger M.cs, retirer les marqueurs, puis git add M.cs git commit # ou git rebase --continue

Le diff combiné

Pendant le conflit, git diff affiche deux colonnes de signes : la première compare à ta version, la seconde à l'autre. Une ligne ++ n'existe dans aucune des deux : ce sont les marqueurs.

Résoudre, c'est écrire

Garder 5, garder 6, ou écrire autre chose : Git ne vérifie rien. git add enregistre le fichier tel qu'il est et ramène l'index à une seule version ; la fusion se termine par un commit ordinaire.

Piège courant Faire git add en laissant un marqueur dans le fichier. Git l'accepte sans broncher et le commit part avec ======= au milieu du code. git diff --check avant d'ajouter signale les marqueurs restés.

Schéma 2 · Le faux conflit

Un fichier entier en conflit pour une ligne

Windows termine les lignes par deux caractères (\r\n), Linux et macOS par un seul (\n). Si un éditeur réécrit un fichier avec l'autre convention, chaque ligne change pour Git, même si personne n'y a touché. La fusion qui suit met tout le fichier en conflit.

Exemple autonome · Git, régler les fins de ligne d'un dépôt# .gitattributes, à la racine * text=auto eol=lf # texte : LF dans le dépôt et sur le disque *.gha binary # jamais converti, jamais fusionné ligne à ligne # puis, une fois, pour renormaliser ce qui est déjà suivi git add --renormalize .

text=auto

Git décide seul si un fichier est du texte (il cherche un octet nul au début). Le texte est rangé en LF dans le dépôt ; sur le disque, il prend la convention du poste, sauf si eol=lf l'impose.

Dans le dépôt, pas dans le poste

Le réglage core.autocrlf dépend de chaque machine ; .gitattributes est versionné et vaut pour tous. C'est lui qui garantit que deux postes produisent les mêmes octets.

Piège courant Ajouter .gitattributes à un dépôt existant sans renormaliser. Les fichiers déjà suivis en CRLF le restent jusqu'à leur prochaine modification, qui apparaît alors comme une réécriture complète : le faux conflit arrive plus tard.

Schéma 3 · Choisir un côté

Quand on ne peut pas combiner

Un binaire (une DLL, un .gha, un .gh) ne se fusionne pas ligne à ligne. Git annonce le conflit, laisse le fichier tel qu'il était sur ta branche et attend qu'on désigne une version entière. Le piège est dans le nom des côtés, qui change de sens selon l'opération.

Exemple autonome · Git, prendre une version entièregit checkout --theirs Magpie.gha # la version de l'autre côté git checkout --ours M.cs # la version de HEAD git add Magpie.gha M.cs git merge --abort # ou tout annuler

Un binaire produit se refait

Si le binaire est construit à partir du code (une compilation), aucun des deux côtés n'est juste : chacun vient d'un code incomplet. On résout le code source, puis on recompile, et c'est ce nouveau fichier qu'on ajoute.

Un conflit par commit rejoué

En rebasage, Git s'arrête sur le premier commit qui bute (mesuré : « Could not apply c7b5f78… marge 6 »). Les marqueurs portent alors le nom du commit, pas celui d'une branche.

Piège courant Taper --ours pendant un rebasage pour « garder mes changements ». C'est la branche de destination qui est « ours » : on jette son propre travail, et le rebasage continue sans rien signaler.

Glossaire

Conflit
Deux changements d'un même passage que Git ne sait pas réunir.
Marqueurs
Les lignes <<<, ===, >>> qui encadrent les deux versions.
Base
La version de l'ancêtre commun, avant les deux changements.
Ours, theirs
Le côté de HEAD et l'autre ; inversés en rebasage.
Fin de ligne
LF (\n) ou CRLF (\r\n), selon le système qui écrit.
