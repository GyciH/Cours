Le concept

Ce qu'un test prouve

Un test automatique exécute un morceau du programme et compare le résultat à ce qu'on attend. Quand il passe, on se sent couvert. Ce cours mesure ce que cette impression vaut, en introduisant exprès des défauts dans le code de Magpie et en regardant lesquels ses tests voient.

45 min de lecture et de QCM Prérequis · 26 tests automatisés Exemples · Magpie web, SnapSet

L'idée en une phrase

Un test prouve que le programme se comporte bien sur les exemples qu'il essaie, et seulement sur eux ; sa valeur se mesure aux défauts qu'il ferait échouer.

L'analogie

Un contrôle de pièces en atelier. La pige « entre » vérifie qu'une cote n'est pas trop grande ; sans la pige « n'entre pas », une pièce trop petite passe. Un contrôle qui n'essaie qu'un côté laisse passer l'autre défaut sans bruit.

À la fin, tu sais

  1. découper un test en trois temps ;
  2. dire ce qu'un test vert prouve ;
  3. mesurer un jeu de tests par mutants ;
  4. repérer un test qui ne peut pas échouer.
À retenir Toutes les mesures de ce bloc ont été faites sur des copies des dépôts, dans le dossier de travail de la session : aucun fichier de SnapSet, Cuttlefish ou Magpie n'a été modifié.

Schéma 1 · Mettre les tests à l'épreuve

Casser exprès pour voir

Le test par mutation retourne la question : au lieu de demander si le code est juste, il demande si les tests remarqueraient qu'il ne l'est plus. On fabrique des copies du code avec un petit défaut chacune (un mutant), on lance les tests sur chaque copie, et on compte celles qu'ils font échouer.

Exemple autonome · Python, le cœur d'un testeur par mutationfor ligne, (avant, apres) in mutations: # « > » → « >= », etc. ecrire(copie, remplacer(source, ligne, avant, apres)) r = subprocess.run(["node", "--test", test]) tue = r.returncode != 0 # un test a échoué : bien vu ecrire(copie, source) # toujours restaurer

Le score de mutation

La part de mutants tués, ici 28 sur 38 non équivalents, soit 74 %. Contrairement à la couverture (cours 112), il ne compte une ligne que si un test dépend vraiment de ce qu'elle calcule.

Des outils tout faits

Stryker (JavaScript, C#) ou PIT (Java) génèrent des centaines de mutants et rangent les survivants par fichier. Le principe est celui du petit script : copier, casser, tester, restaurer.

Piège courant Chercher à tuer tous les mutants. Certains sont équivalents (le programme fait exactement la même chose) et aucun test ne peut les voir. On lit les survivants un par un ; on ne vise pas 100 %.

Schéma 2 · Les frontières

Essayer les deux côtés

Les défauts se logent aux limites : une tolérance, une longueur de liste, une valeur vide. Un cas « au milieu » ne dit presque rien. Les cas qui comptent sont ceux qui encadrent chaque frontière, juste dedans et juste dehors, et de chaque côté.

Exemple autonome · node:test, encadrer une toléranceassert.equal(verdict([1.009, 3, 5], c), true, "juste dedans, au-dessus"); assert.equal(verdict([1.02, 3, 5], c), false, "juste dehors, au-dessus"); assert.equal(verdict([0.991, 3, 5], c), true, "juste dedans, en dessous"); assert.equal(verdict([0.98, 3, 5], c), false, "juste dehors, en dessous");

Le message de l'assertion

Le troisième argument (« hors tolérance ») est ce qu'affiche un échec. Les tests de Magpie le soignent : le jour où l'un casse, il dit quel cas, sans relire le code.

Pile sur la frontière

Tester 1,01 exactement est piégeux : 1,01 − 1 vaut 0,010000000000000009 en virgule flottante (cours 49), un peu plus que 0,01. On teste nettement de part et d'autre.

Piège courant Écrire les cas de test en relisant le code. On reproduit alors ses angles morts : si le code oublie un côté, celui qui le relit l'oublie aussi. Les cas se tirent de la règle (« à 0,01 près »), pas de l'implémentation.

Schéma 3 · Le faux vert

Le test qui ne peut pas échouer

Un test peut passer pour une raison qui n'a rien à voir avec le code testé : il sort avant de vérifier, il vérifie trop tard, ou il compare une valeur à elle-même. Il reste vert quoi qu'on fasse, et rassure à tort.

Exemple autonome · node:test, dire qu'on n'a pas pu vérifiertest("le générateur écrit en LF", (t) => { if (!nodeDisponible()) return t.skip("node absent du poste"); // … vérifications }); // le rapport compte ce test « skipped », pas « ok »

Rouge, vert, puis seulement réécrire

La démarche « test d'abord » écrit le test avant le code : il commence rouge, ce qui prouve qu'il peut l'être, puis le code le fait passer. Après coup, on obtient la même preuve en cassant le code un instant.

Ignoré n'est pas réussi

t.skip() en JavaScript, [Fact(Skip = "…")] ou le paquet SkippableFact en xUnit 2 : le test apparaît « ignoré » dans le rapport. Un return silencieux le montre « réussi ».

Piège courant Compter les tests verts comme une mesure de qualité. Un projet de 600 tests dont un tiers ne peuvent pas échouer n'est pas mieux protégé qu'un projet de 400 : le nombre ne dit rien, les mutants tués disent quelque chose.

Glossaire

Assertion
Une vérification qui fait échouer le test si elle est fausse.
Mutant
Une copie du code avec un défaut introduit exprès.
Score de mutation
La part des mutants non équivalents que les tests font échouer.
Mutant équivalent
Un changement qui ne modifie pas le comportement.
Faux vert
Un test qui passe sans avoir vérifié ce qu'il annonce.
